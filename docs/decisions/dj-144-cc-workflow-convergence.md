## DJ-144: Re-Architect the Claude Code Convergence Driver Around Dynamic Workflows — the Workflow Script Becomes the Parallel Orchestrator *and* the Loop for the Four Convergent Activities (`spec_refinement`, `code_adoption`, `feature_ingestion`, `code_assimilation`); the Scout Still Owns the Convergence *Judgment* While the Script Drives Iteration + Enforces the Injected `max_iterations` Cap; Named Subagents Are Preserved as Workers and Fanned Out Only Over Disjoint Units Behind Phase Barriers; Removes `/goal`, the Harness `OuterLoopRunner`-for-Claude-Code, and the Verdict-Line-as-Harness-Artifact on Claude Code; Codex / Gemini Stay on the DJ-142 Drivers Unchanged — a Fourth Driver for One Runtime, Same Outcome; Folds In a Declared Per-Runtime Minimum-Version Registry (`runtimes-default.yaml` + `.borg/runtimes.yaml`, Version Read from `ClientInfo.version`, Warn-and-Proceed) Generalizing the Workflow v2.1.154 Floor

**Context.** Claude Code shipped **dynamic workflows** (Opus 4.8 era, research preview — https://claude.com/blog/introducing-dynamic-workflows-in-claude-code, docs https://code.claude.com/docs/en/workflows). The runtime lets Claude author a JavaScript orchestration script that a background runner executes: the script fans work out across many subagents (up to 16 concurrent, up to ~1,000 per run), loops until a convergence condition the script itself evaluates, and holds intermediate results in script variables — only the final answer returns to the conversation context. Crucially, and unlike `/goal`, **dynamic workflows are reachable headlessly** (`claude -p` and the Agent SDK), per the docs' permission table ("Bypass permissions, `claude -p`, Agent SDK | Never. The run starts immediately") and the "Turn workflows off" section ("Workflows are available in the CLI, the Desktop app, the IDE extensions, non-interactive mode with `claude -p`, and the Agent SDK"). Requires Claude Code **v2.1.154+**. The keyword trigger (the word "workflow" anywhere in the prompt) is the only documented headless activation path; saved workflows (`.claude/workflows/`, surfaced as `/<name>` slash commands) are interactive-only, matching the general rule that slash commands don't dispatch headlessly. See [[reference-dynamic-workflows-interactive-only]] for the full reachability finding.

This reopens a question DJ-140 closed under duress. [DJ-136](dj-136-per-runtime-idiomatic.md) wanted Claude Code to drive its own convergence loop in-runtime (via `/goal`) rather than through a harness re-dispatch — the runtime-idiomatic stance ([[feedback-runtime-idiomatic-no-lcd]]). [DJ-140](dj-140-headless-convergence-unification.md) discovered `/goal` is an interactive-session-scoped built-in unavailable in the headless `claude-agent-acp` path and unified *all* runtimes' headless convergence on the harness `OuterLoopRunner` (re-dispatch per iteration, reading a plain-text `converged: true|false` verdict line). [DJ-142](dj-142-idiomatic-convergence-drivers.md) then established the governing principle — **consistent convergence *outcome*, idiomatic *driver* per context** — and filled the three driver slots: headless (all runtimes) → `OuterLoopRunner`; interactive · Claude Code → `/goal`; interactive · Codex / Gemini → daemon-side `spec_loop_*` self-loop. Dynamic workflows give Claude Code a *headless-reachable* in-runtime loop-and-fan-out driver — the thing DJ-136 wanted and DJ-140 couldn't have. It is strictly idiomatic to Claude Code (Codex and Gemini have no equivalent), so adopting it for Claude Code only is exactly the DJ-142 pattern, not a violation of it.

**The cost framing is settled and is *not* the deciding factor (chat 2026-05-28).** Dynamic workflows use "meaningfully more tokens," and the `claude-agent-acp` dispatch path bills against Agent SDK credits, not the Max subscription bucket ([[project-anthropic-billing-split]]). The operator's explicit position: the per-bucket charge is an Anthropic decision no user controls; the only lever Locutus exposes is headless-vs-interactive, and developers would rather pay more up front for a correct result than pay less per iteration and push a correct result out across more rounds — which can cost more in aggregate. So cost is acknowledged, documented, and deliberately *not* treated as a reason to withhold the capability. The real design work is convergence-engine de-duplication (a workflow holds its own loop, which competes with `OuterLoopRunner`) and parallel-write coherence on the shared spec graph.

**Decision.** For Claude Code, replace the convergence driver with a dynamic-workflow script for the four convergent activities — `spec_refinement`, `code_adoption`, `feature_ingestion`, `code_assimilation`. The script is the parallel orchestrator and the loop; the named subagents are preserved unchanged as its workers; the scout still owns the convergence judgment while the script drives iteration and enforces the cap. Codex and Gemini keep their DJ-142 drivers verbatim.

1. **A fourth idiomatic driver, same outcome.** This extends the DJ-142 matrix with a Claude-Code-specific row that applies to *both* modes (the workflow is headless-reachable via keyword and interactive via saved slash command), collapsing what was two Claude Code rows into one driver:

    | Context | Driver | Convergence judgment | Cap enforcement |
    |---|---|---|---|
    | Headless · Codex / Gemini | Locutus `OuterLoopRunner` (re-dispatch) | scout verdict line | harness counter (DJ-138 `max_iterations`) |
    | Interactive · Codex / Gemini | agent self-loop via `spec_loop_*` (DJ-142) | scout verdict to `spec_advance_iteration` | daemon counter |
    | **Claude Code (both modes)** | **dynamic-workflow script (in-runtime loop + fan-out)** — *new* | **scout verdict, read by the script** | **script counter against the injected `max_iterations`** |

    Every row still reaches the one outcome DJ-142 fixed: converge (scout reports `converged: true`) or stop at `max_iterations`. The scout's role is unchanged across all drivers — it judges; the driver only re-triggers and counts.

2. **Named subagents are preserved as workers; not collapsed or reshaped (chat 2026-05-28).** `spec-scout`, `spec-decision-elaborator`, `spec-challenger`, `spec-advocate`, the goal-diff matcher, and the rest keep their roles, prompts, and ids — they were hammered out over many iterations and carry clear responsibilities. The workflow script *invokes* them as subagents; it does not absorb their logic. The re-architecture is about **how work is sequenced and parallelized**, not about reshaping the council. The alignment test (below) enforces that the script only ever references known agent ids.

3. **No `spec_loop_*` for Claude Code — the workflow self-evaluates convergence.** The DJ-142 loop-state tools (`spec_loop_begin` / `spec_loop_status` / `spec_advance_iteration`) stay Codex/Gemini-only, exactly as [DJ-143](dj-143-per-runtime-tool-policy.md) restricts them. A dynamic workflow's value proposition is that the script itself evaluates the convergence condition from the scout's verdict and counts its own iterations — there is no need for daemon-side loop-state bookkeeping when the loop lives in the script's own variables. The cap is injected into the script's input (see §6), and the script enforces it. This is the operator's point from the chat: "Isn't one of the value props of dynamic workflows that the agent can determine convergence (or max iterations hit) from the scout alone?" — yes, so Claude Code needs no loop-state tools.

4. **Orchestration model: a phase pipeline with barriers — fan out only over disjoint units, serialize shared-node steps (chat 2026-05-28, Q4 "phase barriers in the script").** The spec graph is shared mutable state and the MCP write path is non-transactional (git is the rollback layer, DJ-138), so uncontrolled parallel writes risk incoherence. The script structures each iteration as a barrier-separated pipeline:

    - **Preamble (one-time, before the loop): goal-layer sync.** For `spec_refinement`, the `GOALS.md` reconciliation (Step 0 of `spec_refinement.md` — dispatch the goal-diff matcher, apply `spec_propose_goal` / `spec_revise_goal` / `spec_delete_goal`, persist the new `goals_md_hash`) runs once before the convergence loop, not per iteration. `GOALS.md` is read-only for the duration of a run, so re-syncing each pass is wasted work (chat 2026-05-28 — "Does the goal layer sync need to run every iteration?" → no). The hash short-circuit already makes a re-sync cheap, but hoisting it to a preamble makes the no-op structural rather than incidental.
    - **Loop body, per iteration, barrier-separated:**
        1. **Survey / scout** (serial) → if the scout reports `converged: true`, break the loop.
        2. **Decide-axes ‖ elaborate ‖ critique** (parallel fan-out) — fan out *only over disjoint units* (e.g. independent axes / independent candidate features), so concurrent subagents never touch the same node.
        3. **Reconcile** (barrier) — join the fan-out; dedup and serialize any writes that would land on a shared node, so a single coherent revision is applied rather than racing partial ones.
        4. **Cascade** (serial where it crosses shared nodes) — apply downstream `spec_revise_*` / drift marks with shared-node writes serialized.
    - **Citation walk (one-time, after the loop converges):** the `.advances` / `.respects` goal-citation pass runs last against the final state, as in `spec_refinement.md`'s Step N+1.

    The rule is uniform: **fan out across disjoint work units; put a barrier before any step that writes a node another branch might also write.** This preserves the spec graph's coherence without introducing transactional spec mutations (which the architecture deliberately omits).

5. **Authoring and resolution (walk [docs/agent-conventions.md](../agent-conventions.md) before writing any of these — [[feedback-agent-conventions-checklist-first]]).**
    - **Pinned workflow script** `internal/scaffold/workflows/<activity>.js` → published to `.claude/workflows/<activity>.js`. As a saved workflow it surfaces interactively as the `/<name>` slash command (`/locutus-refine`, etc.) and runs deterministically (the pinned script, not a regenerated one). This is the interactive Claude Code path.
    - **New headless keyword-trigger playbook** `internal/scaffold/plans/<activity>.claude-code.md` (tier-2 in `ResolvePlaybook`, provider-specific, mode-agnostic) — workflow-shaped prose that contains the word "workflow" so the headless `claude -p` / Agent SDK dispatch triggers a dynamic workflow. Headless cannot invoke the saved script (slash commands are interactive-only), so headless regenerates the orchestration from this playbook each run. This is *not* a determinism regression: the status-quo headless driver (`OuterLoopRunner` re-dispatch) is non-deterministic too ([[reference-dynamic-workflows-interactive-only]]).
    - **Base `<activity>.md` kept** for Codex / Gemini headless (the one-iteration playbook the `OuterLoopRunner` re-dispatches) — unchanged.
    - **Delete `spec_refinement.claude-code.interactive.md`** — the `/goal` wrapper. Its job (interactive Claude Code convergence) is now the saved workflow script's.
    - **Guard `spec_refinement.interactive.md`** (the DJ-142 Codex/Gemini self-loop) so it never resolves for Claude Code — it references `spec_loop_*`, which DJ-143 denies to Claude Code. With the tier-1 `.claude-code.interactive.md` deleted and a tier-2 `.claude-code.md` added, Claude Code interactive resolves to tier-2 (the workflow playbook) before it can reach the tier-3 `.interactive.md`; an assertion in the resolution/publisher test must lock this so a future tier shuffle can't leak the loop-tool playbook to Claude Code.
    - **Alignment test:** the published `.js` for each activity references only known agent ids (§2) and covers the same phase set as the corresponding base playbook (so the workflow can't silently drop the citation walk or the goal-sync preamble).

6. **Dispatch — Option A: take Claude Code off the harness outer loop (chat 2026-05-28, "Go with option A").** `dispatchUsesOuterLoop("claude-code")` returns **false**; Claude Code headless becomes a single ACP dispatch whose playbook (the tier-2 `.claude-code.md`) triggers the in-runtime workflow, which owns the loop. The `max_iterations` cap (from the activity registry, DJ-138, including `.borg/agents.yaml` overrides) is **injected into the playbook body** at dispatch time so the script can enforce the same cap the harness would have. Codex and Gemini keep `dispatchUsesOuterLoop == true` and the `OuterLoopRunner` verbatim. The `runtime == "claude-code"` branch DJ-140 removed from `internal/runner/run.go` returns in spirit — but as "dispatch once, the workflow loops" rather than DJ-136's "the `/goal` evaluator loops."

7. **Teardown on Claude Code (only Claude Code).** Remove, for the Claude Code path: the `/goal` wrapper playbook; the `OuterLoopRunner`-driven re-dispatch; and the reliance on the plain-text verdict line as a *harness* artifact. The verdict line still exists as the scout's convergence signal — the workflow script reads it instead of the harness — so the scout's contract is unchanged; only its *reader* moves from harness to script. None of this touches Codex / Gemini, where the verdict line and `OuterLoopRunner` remain the headless driver.

8. **Permissions — the ACP `Policy` is the primary lever (chat 2026-05-28 correction).** Locutus is the ACP *client*; the dispatched runtime's tool calls route through `internal/dispatch/acp/client.go`'s `RequestPermission`, which calls `internal/dispatch/policy/policy.Policy.Decide`. The council's spec tools are already permitted there, so workflow-spawned subagents that call `mcp__locutus__spec_*` should be covered by the same policy — provided their calls route through the ACP client (this is the first open verification item). The Policy must decide *cheaply* for workflow use (no per-call validator-LLM round-trip, which would multiply across up to 16 concurrent subagents). A `settings.json` allowlist (`mcp__locutus__*`, `Bash`, `Read`, `Task`) is the **fallback** for any workflow-subagent call that turns out to bypass the ACP client and hit Claude Code's own permission rules directly (the docs note that in `claude -p` / Agent SDK, "tool calls follow your configured permission rules without interactive confirmation").

9. **Degradation guard — a declared per-runtime minimum-version registry, warn-and-proceed (chat 2026-05-28).** Dynamic workflows require Claude Code **v2.1.154+**; the keyword trigger silently no-ops on older versions or when disabled (`CLAUDE_CODE_DISABLE_WORKFLOWS=1` / `"disableWorkflows": true`), falling back to a single non-looping pass that can be mistaken for convergence-in-one-iteration. DJ-144 is the first time Locutus hard-depends on a version-gated runtime feature (prior to it, "if the runtime speaks MCP/ACP at all, it works"), and the failure is *silent* — which is exactly what makes detection worth generalizing rather than hardcoding the one constant.

    - **Declared registry, not a hardcoded constant.** Minimum runtime versions live in a YAML registry following the DJ-138 precedent (`internal/activity/agents-default.yaml` embedded default + `.borg/agents.yaml` operator override): an embedded `internal/activity/runtimes-default.yaml` + a `.borg/runtimes.yaml` override, keyed by runtime —

        ```yaml
        claude-code: { min_version: "2.1.154" }
        codex:       { min_version: "..." }
        gemini:      { min_version: "..." }
        ```

        Version floors are *pure data* (a version string per runtime), with none of the code-behavior coupling that forced DJ-143's tool policy out of `tools.yaml` and into call-time `requireRuntime` wrappers — so YAML genuinely fits here even though `tools.yaml` itself did not ship as YAML. The registry has room to grow beyond the workflow case: hooks (DJ-136) and future runtime-gated affordances have latent floors too. (Whether a single per-runtime floor suffices, or per-feature floors are eventually needed, is deferred — one floor per runtime, set to the highest feature we depend on, is the v1 posture.)

    - **Detection reuses the DJ-143 channel.** The runtime version is read from `ClientInfo.version` at MCP `initialize` — the same `Implementation` struct DJ-143 already reads `ClientInfo.name` from for runtime identification — so detection covers both modes (headless dispatch and interactive `locutus mcp` both perform an MCP handshake against the daemon) with no `--version` subprocess probe. *Verification item:* confirm `ClientInfo.version` carries the coding-agent version (Claude Code's) and not the MCP client-library/SDK version; if it is the SDK version, fall back to a `--version` probe at dispatch (headless-only, which is the path workflows matter most on). See *Open verification items*.

    - **Warn-and-proceed, not block (chat 2026-05-28).** When the detected version is below the floor (or unparseable, or absent), Locutus logs a loud warning naming the runtime, detected version, and required floor — then dispatches anyway. Blocking would be hostile for soft-degrading features: a sub-floor Claude Code still completes the activity, just as a single non-looping pass instead of a parallel convergence loop. Nothing today is a true hard requirement Locutus would newly enforce by refusing to run (a runtime too old to speak MCP/ACP fails the handshake on its own). Fail-open on undetectable/unparseable versions — never block on a version we couldn't read. If a genuine hard floor appears later, a per-entry `enforce: block|warn` flag is the grow-into (not built now).

**Resolved design questions** (chat 2026-05-28):

1. **Scope: all four convergent activities, Claude Code only** (Q1 answer "All convergent activities, CC only"). `spec_bias` is *not* in scope — it is a single-pass write-cascade, not a converge-to-fixed-point loop (DJ-138), so it has no convergence driver to re-architect. The justify activity is read-only and one-shot. Codex / Gemini keep DJ-142 across all activities.

2. **Re-architect for parallelism; preserve the named subagents** (Q2 answer). The win is parallel fan-out + an in-runtime loop, not a reshaped council. See Decision §2.

3. **No `spec_loop_*` for Claude Code** (Q2 follow-up). The workflow self-evaluates convergence from the scout and counts its own iterations; daemon-side loop-state is the Codex/Gemini idiom, kept denied to Claude Code by DJ-143. See Decision §3.

4. **Saved script interactive, keyword headless** (Q3 answer). Two authoring artifacts: the pinned `.js` (deterministic, interactive slash command) and the `.claude-code.md` keyword playbook (headless, regenerates the script each run). Saved workflows can't be invoked headlessly; keyword can't pin a script — so each mode uses the path available to it. See Decision §5.

5. **Phase barriers in the script** (Q4 answer, recommended option). Fan out over disjoint units; barrier before shared-node writes; serialize/dedup the join. See Decision §4.

6. **Goal-layer sync is a one-time preamble, not per-iteration** (chat 2026-05-28). `GOALS.md` is read-only during a run; re-syncing each pass is wasted work even with the hash short-circuit. See Decision §4 preamble.

7. **Dispatch Option A** (chat 2026-05-28). Take Claude Code off `dispatchUsesOuterLoop`; single dispatch, workflow owns the loop; inject the cap into the playbook body. See Decision §6.

8. **Cost is acknowledged and explicitly not a gate** (chat 2026-05-28). Documented as a consequence; the only Locutus-exposed lever (headless vs interactive) is the operator's to pull. See Context.

**Alternatives considered:**

- **Leave Claude Code on the DJ-140 / DJ-142 drivers (`/goal` interactive, `OuterLoopRunner` headless); don't adopt workflows.** Rejected — workflows are the idiom DJ-136 originally wanted for Claude Code and are now headless-reachable, so withholding them is the LCD posture DJ-142's principle argues against. The cost concern that might have justified waiting was explicitly set aside by the operator.

- **Adopt workflows for Claude Code *and* try to give Codex / Gemini an equivalent (uniform "everyone parallel-loops") driver.** Rejected — Codex and Gemini have no dynamic-workflow equivalent; forcing a shared abstraction is exactly the lowest-common-denominator design [[feedback-runtime-idiomatic-no-lcd]] rejects. A fourth driver for the one runtime that has the capability is the idiomatic move.

- **Collapse / reshape the named subagents into the workflow script's inline logic.** Rejected (Q2) — the council roles are stable and hard-won; the script orchestrates them, it doesn't absorb them.

- **Use the DJ-142 `spec_loop_*` tools as the Claude Code loop driver too (uniform loop-state).** Rejected — defeats the workflow's self-contained-loop value prop, and DJ-143 deliberately denies those tools to Claude Code. The script counts itself.

- **Run both the workflow loop and the harness `OuterLoopRunner` for Claude Code (workflow inside each harness iteration).** Rejected — two convergence engines stacked is redundant and double-counts iterations against the cap. Option A removes the harness for Claude Code so there is exactly one loop.

- **Uncontrolled parallel fan-out (no barriers), relying on git rollback to repair incoherent concurrent writes.** Rejected — git is the *architectural* rollback layer for a whole run, not a per-write conflict resolver; racing writes on a shared node produce silently-wrong state, not a clean rollback point. Phase barriers prevent the race instead of repairing it.

- **Re-sync the goal layer every iteration.** Rejected (resolved-question 6) — `GOALS.md` is read-only during a run; the preamble runs it once.
