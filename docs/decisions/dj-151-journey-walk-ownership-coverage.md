# DJ-151: Persona Journey-Walk Enumeration + Ownership-Test Coverage Judgment in `spec-coverage-critic` — Amends DJ-150 After the WinPlan Sufficiency Audit Showed the Critic Converging With the Application Shell Unowned; Citation-Grounded Enumeration Is Structurally Biased Against Tacit Obligations (Authoritative Sources Exist for A2P/CPRA/WCAG, Not for "Apps Need a Sign-In Page"), So the Critic Gains a Second Enumeration Mode That Walks Each Derived Persona Through the Full Deliverable Lifecycle; Prose-Coverage Judgment (DJ-150 RQ3) Is Reversed to an Ownership Test — Covered Means a Feature Claims the Surface as Its Deliverable With an Acceptance Criterion Exercising It, Never Ambient Mention; Spec Layer Confirmed as the Owning Layer for Deliverable Boilerplate (Explicit and Challengeable Over Implicit); Personas Are Derived Per-Run, Not Persisted; Scaffold-First Adopt and Walkthrough Verification Rejected as Owners and Deferred Respectively

**Status:** settled (designed 2026-07-06; no code yet). Amends [DJ-150](dj-150-spec-coverage-critic.md) — reverses its resolved question 3 (prose coverage) and extends its resolved question 1 (grounded enumeration as the sole enumeration mode). DJ-150's dispatch cadence, findings flow, session-state persistence posture, granularity discipline (§7), and topology-vs-process bias check (§8) all stand unchanged.

**Context.** DJ-150 shipped and demonstrably works for what it enumerates: winplan's 2026-06-02 refine run surfaced 5 obligations, the scout dispositioned 3 as strategy-owned wontfixes, and 2 became real features (`feat-data-deletion-lifecycle`, `feat-degraded-mode-banner`) with the loop converging in 2 iterations. But a full sufficiency audit of winplan's `.borg/` + `.locutus/` artifacts (2026-07-06) showed that same converged run had left the application shell entirely unowned. The approach layer was audited and exonerated — of 13 feature approaches, 5 fully cover their parents and 8 are mostly-complete with narrow edge losses; 9 of 10 strategy approaches likewise; zero pairs show significant gaps. The insufficiency is one layer up, in what the feature set never captured: **no feature owns the sign-in/sign-up surface, the navigation shell / information architecture, the unauthenticated public entry, the design-system realization, or error/empty/first-run states.** The code faithfully reflects those holes: 5 UI pages totalling ~240 lines, zero CSS anywhere in the repo, no `middleware.ts`, every dashboard deep-link 404ing, 10 of 15 features with no UI page at all — wrapped around a genuinely mature domain engine (25K lines in `lib/`, 88 test files). The critic reported **zero uncovered obligations** over this graph.

Two root mechanisms, both structural rather than prompt-tuning failures:

1. **The citation-grounding discipline filters out the tacit.** DJ-150's enumeration requires every obligation to resolve to an authoritative source found via web search. That selects precisely for *documented* obligations — A2P 10DLC, CPRA §7051, WCAG — which is exactly the class winplan's spec is rich in, because the critic finds them well. Nobody writes an authoritative standard saying "your web app needs a sign-in page and a nav bar"; boilerplate is tacit *because* it is too obvious to document. The current prompt's "thoughtful person" heuristic (a DJ-150 amendment) invites the model to notice tablestakes but still funnels every candidate through the citation gate, where the tacit ones die. The winplan evidence: the critic surfaced "degraded-mode status banner" (documentable — status-page practice) and never emitted "users can sign in" or "users can move between features" as obligations at all, so no coverage judgment ever ran on them.

2. **Coverage is judged by mention, not ownership.** Winplan's feature bodies discuss Clerk sign-in constantly ("a manager signs in via Clerk and creates a workspace…") as ambient context. A critic reading prose in natural language sees authentication *discussed everywhere* and judges the concern addressed — but no feature *claims the surface as its own deliverable*, so no approach specifies it, no code builds it, and nothing downstream ever surfaces the absence. DJ-150's coverage-judgment threshold ("substantively addresses… not a passing mention") gestures at this but gives the critic no structural test to apply.

The user's framing generalizes beyond web apps: "iPad app" carries platform boilerplate (App Store distribution, install/onboarding, offline behavior, platform navigation idioms) that a framework *decision* (the axis machinery handles React Native vs Swift fine) does not pull in as owned surfaces. The gap is the deliverable shape's implied *surface set*, whatever the shape.

Applying DJ-150 §8's own topology-vs-process test to the fix: the recognized human-practice artifacts for boilerplate are **starter scaffolds** (boilerplate by construction — `create-next-app`, Xcode templates) and **user-journey walkthroughs** (day-one journey mapping — "a new user types the URL; then what?"). Both are process artifacts. The design conversation resolved the owning layer explicitly: **the spec layer owns deliverable boilerplate.** "Of course" features are written down precisely because "of course" is sometimes wrong (a kiosk app wants no self-serve sign-up), and explicit feature nodes keep the graph transparent, challengeable by the operator, and traceable through approaches to code. Scaffold-by-construction was rejected as the owner (the spec would no longer describe the application); walkthrough *verification* was deferred to a future DJ (it discovers gaps late, after a build, and entangles DJ-068's status semantics — but it remains the complement that would catch `live`-status overclaiming, which this DJ does not address).

**Decision.** Amend `spec-coverage-critic` with a second enumeration mode — the persona journey walk — and replace prose-coverage judgment with an ownership test. Same agent, same dispatch cadence and position, same findings flow. No new node kinds, no new MCP tools, no new persistence.

1. **Persona journey walk as a co-equal enumeration mode.** Within its existing single dispatch (per deliverable shape, Phase 0 of each refine iteration before the scout; the inherited assimilate step likewise), the critic first derives the deliverable's personas per-run from the goal layer and feature prose — winplan's would be roughly *prospective visitor, admin/manager, staff, volunteer*. Personas are **not** persisted and there is no persona node kind: personas are a recognized PM artifact, but nothing in the graph consumes them yet, and per the no-aspirational-shape discipline they stay derived (like deliverable shapes are today) until a consumer exists. For each persona the critic walks the full lifecycle — **arrival/acquisition → authenticate → orient/navigate → core loop → empty/first-run states → failure states → account/workspace management → departure** — and emits every journey step the deliverable must support as an obligation. The walk is shape-idiomatic by construction: a hosted web app's walk starts at a URL (public entry, sign-up); a mobile app's starts at the App Store (distribution, install, onboarding, offline); an API's starts at documentation and a key; a CLI's at install and `--help`.

2. **Dual provenance in `CoverageReport`.** `ObligationEntry` gains a `source` field: `journey | grounded`. Journey obligations are grounded in the walk itself and carry `journey_provenance: {persona, step}` in place of web citations; grounded obligations keep the existing `citations[]` minItems-1 discipline and the web-search pass continues unchanged (it demonstrably finds the documented/regulatory class well — winplan's A2P and CPRA features came from it). Exactly one provenance kind is populated per entry, keyed by `source`. The citation gate no longer touches journey entries, which is the point: it was the filter killing the tacit. `CoverageReport` remains prompt-declared (no Go schema registry exists; the frontmatter contract test in `internal/scaffold/scaffold_test.go` locks the binding, not the shape).

3. **Ownership-test coverage judgment — reverses DJ-150 resolved question 3's prose coverage.** An obligation is covered only when at least one feature's *declared scope claims the obligation's surface or concern as its deliverable* — it appears in that feature's title, summary, or acceptance criteria as something the feature builds — **and** at least one acceptance criterion exercises it. Ambient mention, assumed-as-context prose ("a manager signs in via Clerk and then…"), and aspirational language never count. The judgment remains natural-language and per-run; the parts of DJ-150 RQ3 that rejected a `covers` citation slice and persistent obligation slugs stand untouched — this changes what the critic's judgment *tests for*, not where anything persists. The existing asymmetry rationale carries over and sharpens: a false *uncovered* is recoverable (the scout dispositions strategy-owned or mis-scoped obligations as wontfix — the June 2 run did exactly this for 3 of 5), while a false *covered* silently leaves a gap that nothing downstream will ever surface.

4. **Critic input gains acceptance criteria.** The ownership test needs them: the dispatch input's features array changes from `{id, title, summary, body_excerpt}` to `{id, title, summary, acceptance_criteria, body_excerpt}`. Acceptance criteria are short, structured, and load-bearing for the ownership judgment; the ~500-char `body_excerpt` economy stays for everything else. All playbook files that carry the dispatch prose update together: `spec_refinement.md`, `spec_refinement.claude-code.md`, `spec_refinement.interactive.md`, `code_assimilation.md`, `code_assimilation.claude-code.md`.

5. **Granularity discipline extends to journey steps.** DJ-150 §7 applies unchanged: a journey step becomes a *category-level* obligation ("failure states exist and are owned"), not an implementation task ("add `error.tsx`"). The walk structure does not license finer granularity; it licenses different *coverage* — the steps nobody documents.

6. **Everything downstream is unchanged.** Uncovered obligations flow into the reconcile/cascade steps exactly as the DJ-150 amendments wired them (convergence-blocking input to the scout; the elaborator revise pass extends an existing feature's scope or proposes a new feature via `spec_propose_feature`); DJ-138's cascade marks dependent approaches drifted on feature revisions; DJ-087's synthesize-on-adopt materializes approaches for new features on the next adopt run. Assimilate inherits automatically — same critic, same step.

7. **Expected first-run effect, stated honestly.** Re-refining an existing project will propose the "of course" features — for winplan, plausibly a public landing/entry feature, an auth-surface feature, an app-shell/navigation feature, a design-system-realization feature, error/first-run-state ownership. Feature-count growth with obvious-seeming entries is the intended behavior, not noise: each entry traces to a named persona's named journey step, and the operator can veto any of them. That veto surface is precisely why the spec layer was chosen as owner.

## Resolved design questions

1. **Which layer owns deliverable boilerplate — spec, synthesis scaffold, or verification?** Spec layer. Explicit feature nodes keep assumptions challengeable ("of course" is sometimes wrong) and keep the graph → approach → code trace complete. Scaffold-by-construction rejected as owner: boilerplate the spec never states is boilerplate the operator never sees or vetoes, and the spec stops describing the application. Verification-layer walkthrough deferred to a future DJ: it catches everything including `live`-status overclaiming, but discovers gaps only after a build and entangles DJ-068's status lifecycle — it complements spec ownership rather than substituting for it.

2. **Journey walk replaces or augments grounded search?** Augments. The two modes have disjoint failure modes: grounding finds the documented and misses the tacit; the walk finds the tacit and has no access to the regulatory. Winplan evidence supports keeping both — the A2P/CPRA/retention features exist because grounded enumeration works for its class.

3. **Same critic or a new dedicated shell-critic agent?** Same critic. A second agent would mirror DJ-129's one-critic-per-dimension pattern but doubles dispatch count per iteration, and its findings land in the same revise-pass input where they would overlap and need deduplication. One dispatch, two enumeration modes, one merged `CoverageReport` — the orchestration already wired for DJ-150 carries it without playbook restructuring.

4. **Ownership-test strictness — flat test, or two-tier (ownership for surfaces, prose for cross-cutting constraints)?** Flat ownership test for v1. Cross-cutting constraint obligations (retention windows, isolation guarantees) that legitimately live in strategies will read as uncovered under the flat test — and the scout's existing disposition valve (wontfix: strategy-owned, mis-scoped) already absorbs exactly this class, as the June 2 run demonstrated three times. Two-tier judgment adds a classification burden on the critic that the valve makes unnecessary. Revisit only if wontfix-noise dominates real findings in practice.

5. **Where do personas come from, and do they persist?** Derived per-run from the goal layer + feature prose within the critic's dispatch, like deliverable shapes are today. Not persisted; no persona node kind. Personas *are* a recognized PM artifact — they pass the DJ-150 §8 test — but no graph consumer exists yet, and aspirational shape is dead weight per project discipline. If a future consumer emerges (e.g., per-persona acceptance walkthroughs at verification time), promotion to a node kind gets its own DJ.

6. **Journey scope — entry path only, entry + failure states, or full lifecycle?** Full lifecycle (arrival through departure, including empty/first-run and failure states and account management). Winplan's misses were not confined to the entry path: no error/not-found pages, no settings surface, no way to populate an empty fresh workspace. The narrower scopes rely on grounded search catching what the walk skips, which is the failure mode being fixed.

7. **New DJ or another DJ-150 in-place amendment?** New DJ. The recent DJ-150 amendment commits refined its design mid-implementation; this change *reverses two resolved questions* on field evidence from a full sufficiency audit — the DJ-141/DJ-142/DJ-144 follow-up pattern, keeping DJ-150's record honest about what was believed on 2026-05-31 versus what the first real deployment taught.

8. **Idempotency across re-runs.** The journey walk should be *more* stable run-to-run than the grounded pass: personas and lifecycle stages barely change on a settled graph, so a converged project re-running `refine goals` walks the same journeys, finds the same owners, and returns zero uncovered obligations. It re-fires with real findings when a feature loses scope that owned a step, when the goal layer changes the persona set, or when the deliverable shape itself changes. DJ-150's grounded-pass stochasticity posture (§6, RQ6) is unchanged.

## Alternatives considered

- **Scaffold-first adopt (phase 0 instantiates the platform's canonical starter; boilerplate exists by construction).** Rejected as the owning layer. It is the strongest human-practice analog — nobody forgets the sign-in page when starting from a template that has one — but it makes the shell implicit: the spec no longer describes the application, the operator never sees or vetoes the assumed surfaces, and spec→code traceability breaks exactly where DJ-150-class gaps live. May return as an adopt *implementation detail* (how the runtime realizes shell-owning features) in a future DJ; never as the source of truth.

- **Verification-layer journey walkthrough (adopt's verify step drives the built app end-to-end as a day-one user before any state record can assert `live`).** Deferred, not rejected — it is the complement this DJ deliberately does not attempt. The winplan audit's third finding (state records asserting `live` for an application with no sign-in path, because unit tests over seams satisfied DJ-068's `passed → live` mapping) is untouched by better enumeration and needs its own DJ against DJ-068's status semantics. Spec-layer ownership fixes what gets specified; it does not fix what `live` claims.

- **Registry of boilerplate obligations per deliverable shape.** Re-rejected on DJ-150 RQ1's unchanged grounds. The journey walk is discovery, not a canned list: the walk's *structure* (personas × lifecycle stages) is fixed and generalizes across shapes, but its *content* is derived from this project's goal layer and features per run. A registry would pre-bake the author's current notion of "what a web app needs" and silently degrade as shapes evolve.

- **Dedicated shell-critic agent alongside the existing critic.** Rejected — resolved question 3 above. Dispatch cost and revise-pass finding overlap without any capability the merged mode lacks.

- **Journey walk replaces grounded search entirely.** Rejected — resolved question 2 above. Loses the documented/regulatory enumeration class that demonstrably works.

- **Keep prose coverage but require the critic to name a primary owner per covered obligation.** Rejected as the softest variant of the ownership test: it relies on prompt discipline to resist mention-as-coverage rather than giving the critic a structural test ("which feature's declared scope claims this? which acceptance criterion exercises it?"), and the winplan failure is precisely a prompt-discipline-was-not-enough failure.

Dispatch position, cadence, and downstream handling unchanged.

### Documentation

The workflow diagram's critic node label updates if it names enumeration mechanics.

### Not changed

- `internal/spec/`, `internal/mcp/`, `internal/agent/`, `internal/state/` — no node kinds, no tools, no store or state changes. Same non-surface as DJ-150.
- `internal/activity/agents-default.yaml` — the critic is already registered for both activities; no registry change.
- Dispatch cadence and position — Phase 0 per deliverable shape per iteration in refine; the inherited assimilate step. The walk runs inside the existing dispatch; no new dispatch points, no standalone verb, nothing at adopt or import time.

### Operational

- The critic's single dispatch gets longer (persona derivation + walk + grounded pass in one call) but no new dispatches are added; DJ-150's cost note (one fast-tier grounded call per shape per iteration) still holds with a somewhat larger token count per call. If the combined call starts hitting the agent's 3m timeout on large feature sets, the timeout is the first knob, splitting the modes into two dispatches the second.
- First re-refine on existing projects surfaces shell obligations that were previously invisible: operators should expect a burst of proposed "of course" features (entry surface, auth surface, navigation, error/first-run ownership) on the first DJ-151 run, each traceable to a persona journey step. Rollout note, not a bug.
- Refine iteration counts may grow on projects with unowned shells — same correct-behavior posture as DJ-150's operational note.

### Quality

- Resolves the winplan shell gap at the layer the operator chose to own it: a re-refine should enumerate entry/auth/navigation/failure-state obligations from the visitor and member walks, find no owning features under the ownership test, and drive the elaborator to propose them — after which adopt's DJ-087 path synthesizes approaches and the next audit's "10 of 15 features have no UI page" collapses to features that own pages.
- The ownership test eliminates the mention-as-coverage failure class independently of enumeration: even a grounded obligation ("accessibility") can no longer be judged covered by ambient WCAG name-drops in feature prose.
- Journey provenance makes every tacit obligation auditable — a finding reads "visitor, arrival step" instead of citing a URL, and the operator can judge the persona and step directly.

## Future work

- **Walkthrough verification DJ.** Adopt-side end-to-end journey verification (drive the built deliverable as each persona; Playwright for web, simulator for mobile) gating state-record status — the fix for `live` overclaiming that this DJ explicitly does not attempt. Entangles DJ-068's status lifecycle; likely introduces an honest intermediate status for "implemented against seams, production side not wired."
- **Persona promotion.** If a consumer for persisted personas emerges (per-persona verification walks above being the obvious candidate), promote personas to graph nodes in their own DJ; they pass the §8 test already.
- **Two-tier coverage judgment.** If flat-ownership false-uncovered noise (cross-cutting constraint obligations repeatedly dispositioned wontfix) dominates real findings, add the surfaces-vs-constraints split from resolved question 4.
- **Layer-coherence critic.** The winplan audit's strategy-side finding — parameter/wording drift between layers (Neon plan-tier drift, ZDR posture wording, tier↔model mapping inconsistencies across sibling approaches) — is a different critic shape (cross-node consistency, no enumeration) and gets its own DJ if pursued.
- **SpecStore in-flight commit durability.** The June 2 session's operator note — `feat-degraded-mode-banner` failing to persist across two consecutive runs — is an unexplained dropped-write symptom in the daemon/session path, orthogonal to this DJ; track as a bug investigation.
