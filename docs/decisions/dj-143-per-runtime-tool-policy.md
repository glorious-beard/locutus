## DJ-143: Per-Runtime Tool Restriction at Call Time via `requireRuntime` Wrapper + Sharpened Tool Descriptions; Runtime Identified from MCP `initialize` `ClientInfo.name`; Mode Carried Through `LOCUTUS_MODE` Env → `_meta["locutus.mode"]` Forward — Follow-Up to DJ-142

**Status:** settled (designed 2026-05-28; revised same day after discovering an MCP go-sdk constraint; no code yet). Follow-up to [DJ-142](dj-142-idiomatic-convergence-drivers.md), which shipped the three idiomatic convergence drivers (`/goal` for Claude Code interactive; `OuterLoopRunner` for all headless; `spec_loop_*` daemon tools for Codex/Gemini interactive self-loop) but registered the `spec_loop_*` tools globally on the daemon, so Claude Code interactive sessions saw them too.

**Context.** DJ-142 unified the convergence story across three runtime + mode contexts. The `spec_loop_begin` / `spec_loop_status` / `spec_advance_iteration` MCP tools were added on the daemon to give Codex/Gemini interactive runtimes a server-side loop counter for their self-loop tier-3 playbook (`spec_refinement.interactive.md`). Claude Code interactive uses `/goal` instead and is **not** supposed to touch those tools — its published slash-command wrapper (`spec_refinement.claude-code.interactive.md`) explicitly tells the agent *"do not loop manually; the evaluator owns the iteration cadence."*

The tools were registered globally on the daemon at startup, so they appeared in every connecting client's `tools/list` regardless of runtime. The tools' registered `Description` strings start with *"Begin (or recover) an interactive self-loop run…"* — language that reads to any interactive-session agent as an invitation to use them. The concrete failure surfaced on the first real winplan run after DJ-142 shipped: an operator invoked `/locutus-refine` inside Claude Code. The model received the `/goal`-wrapper slash-command body ("do not loop manually") AND saw `spec_loop_*` in its tool list with "interactive self-loop run" in the descriptions, called `spec_advance_iteration`, got back `iteration: 1/20, continue: true`, and then resolved the contradiction by deferring to the wrapper's explicit "evaluator owns cadence" directive — stopping after one iteration, waiting for an evaluator that prior runs had shown can drive the loop correctly when `spec_loop_*` isn't in the way.

The root cause is not in `/goal`, the wrapper, or the playbook — each is correct under its intended `(runtime, mode)`. The defect is that **DJ-142's loop tools are exposed on an axis that doesn't match their intended consumer**, with no mechanism on the daemon to scope tool exposure per connecting client.

**The MCP go-sdk constraint we discovered while planning.** The initial DJ-143 draft proposed a `tools.yaml` config + per-session `tools/list` filter + call-time `tools/call` guard. Investigation of `github.com/modelcontextprotocol/go-sdk v1.6.1` showed the SDK's tool registry is server-global, not per-session: `Server.AddTool` and `Server.RemoveTools` both mutate one shared registry, the internal `listTools` handler is not overridable via `ServerOptions`, and there is no public per-session tool-registration API. Per-session `tools/list` filtering is not supportable without forking the SDK or building a custom JSON-RPC interceptor underneath it — neither of which is justified for a single runtime-scoped tool family today. Call-time enforcement IS supportable via `ServerSession.InitializeParams()` from inside a tool handler. The design below picks the SDK-supported half and compensates for the missing list-filter half by sharpening the tool descriptions so the agent has a strong textual signal at list-time, paired with a hard structural enforcement at call-time.

**Decision.** A small session-context module captures runtime + mode at `initialize` time. Each runtime-scoped tool is registered with a one-line `requireRuntime` wrapper that enforces the runtime allowlist at call time. The tool's own `Description` string names its intended runtime audience so the agent has a textual signal at list-time. No new config file, no policy loader, no publisher emit — the runtime restriction lives where it's enforced.

1. **Runtime identification at MCP `initialize` via `ClientInfo.name`.** The MCP protocol's `initialize` exchange already carries `clientInfo.name` — Claude Code, Codex, and Gemini each identify distinctly. The go-sdk exposes the populated params via `ServerSession.InitializeParams()` for any handler that holds a `*ServerSession`. The daemon reads this once at session start, normalizes (lowercase, trim), and stores it on the session via a side-channel `sync.Map` keyed by session pointer (the SDK does not expose user-attachable session metadata). No new MCP-spec extension; using a field the protocol already requires every client to send.

2. **Mode carried through `LOCUTUS_MODE` env var, forwarded via `_meta["locutus.mode"]`.** MCP's `initialize` carries no mode field, so the path is:
   - **ACP harness** (`internal/runner/loop.go`, headless-dispatch path) sets `LOCUTUS_MODE=headless` in the env it passes to the spawned `locutus mcp` bridge subprocess.
   - **Bridge** (`cmd/mcp.go`) reads `os.Getenv("LOCUTUS_MODE")` once at startup. Empty/unset → `"interactive"` (the operator-typed-slash-command default). Forwards the resolved value to the daemon as `_meta["locutus.mode"]` on its `initialize` request — MCP allows arbitrary `_meta` fields and the `locutus.` namespace prefix avoids collision with any future MCP-spec field.
   - **Daemon** reads `_meta["locutus.mode"]` from `InitializeParams()` alongside `clientInfo.name`, normalizes, stores both on the session-side map.

   No CLI-surface change to `locutus mcp`. No per-runtime MCP-descriptor change — every runtime's published descriptor still invokes the same bridge binary, and operator-typed sessions get the bridge's default (`interactive`).

3. **`requireRuntime` wrapper at tool registration.** A small adapter that takes an allowlist of runtime names and a tool handler, returns a wrapped handler. At call time it looks up the calling session's stored runtime, returns a clear MCP error if the runtime is not in the allowlist, otherwise delegates to the inner handler. Used to register the three `spec_loop_*` tools as Codex/Gemini-only:

   ```go
   mcp.AddTool(server, &mcp.Tool{
       Name:        "spec_loop_begin",
       Description: descSpecLoopBegin,  // sharpened — see §4
   }, requireRuntime(loopBeginHandler, "codex", "gemini"))
   ```

   The wrapper makes the runtime restriction visible at the registration site — one line per restricted tool, grep-able and adjacent to the tool's name and description. The handler itself stays runtime-agnostic. The deny error names the runtime, the calling session's mode, the tool name, and a docs reference so an operator hitting it has a clear next step: `"tool 'spec_loop_begin' is not exposed to runtime 'claude-code' (mode=interactive); see docs/runtime-affordances.md § Tool-Restriction"`. An unknown runtime (any client whose `ClientInfo.name` isn't recognized) is treated as not-in-allowlist for restricted tools — restricted tools are opt-in by runtime, conservatively.

4. **Sharpened tool descriptions provide the list-time signal.** Each restricted tool's `Description` constant gains a leading sentence naming the runtime audience and contrasting against the wrong audience. For the three `spec_loop_*` tools:

   > For **Codex** or **Gemini** *interactive* self-loop only. Claude Code uses `/goal` to drive the loop and must not call these tools — calling from Claude Code returns a runtime-restriction error.

   The description is what every connected client sees in its `tools/list` regardless of runtime (the SDK constraint we couldn't work around). Sharpening it makes the textual signal an explicit warning rather than an invitation. Paired with the call-time enforcement in §3, this kills the diagnosed failure mode: the agent's invitation-by-description disappears, and a misfire returns a clear runtime-restriction error.

5. **One new file, one infrastructure module, two existing-file edits.** Total code surface:
   - **New:** `internal/mcp/session_context.go` — an `InitializedHandler` reads `ClientInfo.name` + `_meta["locutus.mode"]` from `ServerSession.InitializeParams()`, normalizes, stores on a package-level `sync.Map` keyed by `*ServerSession`. Exposes `SessionRuntime(ss *mcp.ServerSession) (runtime, mode string)` for handlers to read, and `requireRuntime(handler ToolHandler, runtimes ...string) ToolHandler` for the registration-site wrapper.
   - **Modified:** `internal/mcp/server.go` — wire the `InitializedHandler` into `ServerOptions`. `internal/mcp/tools_loop.go` — wrap the three loop-tool registrations in `requireRuntime("codex", "gemini")` and update each `desc...` constant with the sharpened leading sentence.
   - **Modified:** `cmd/mcp.go` — read `LOCUTUS_MODE` env once at startup, forward via `_meta["locutus.mode"]` on the bridge's `initialize` request; debug-log the resolved `(runtime, mode)` so an operator inspecting logs sees what the daemon received.
   - **Modified:** `internal/runner/loop.go` (and the ACP-dispatch wrapper) — set `LOCUTUS_MODE=headless` in the env passed to the spawned `locutus mcp` bridge.

6. **Operational cleanup for the DJ-142 leak.** The diagnostic winplan run advanced the daemon's in-memory loop counter for `(Claude Code session, spec_refinement, goals)` to iteration 1. Before DJ-143 lands, an operator restarting the daemon clears it. After DJ-143 lands, the same scenario can't recur — the `requireRuntime` wrapper on `spec_advance_iteration` refuses any call from a Claude Code session before it can touch the shared loop store.

**Resolved design questions** (chat 2026-05-28):

1. **Why not a `tools.yaml` config file?** The original draft proposed one. It was load-bearing under "per-session `tools/list` filter + call-time guard" because the policy file was the input to both gates. Once per-session `tools/list` filtering came off the table (SDK constraint, see Context), the config file became indirection without a consumer — a wrapper at the tool's registration site is exactly as expressive for one tool family and avoids the loader, the canonical-vs-project file pair, the publisher emit, and the resolution rules (deny-wins, wildcards, defaults). Per [[feedback-no-aspirational-fields]] — one runtime-scoped tool family today, no per-project override need (the rule is determined by runtime architecture, not project preference). If a future need surfaces (many runtime-scoped tools, or genuine per-project overrides), extracting `requireRuntime` registrations into a config-driven loader is mechanical.

2. **Filter mechanism: detect at MCP `initialize` via `ClientInfo.name` (option A), not a bridge-passed `--runtime` flag (option B).** Rejected B as parallel-with-publisher symmetry that doesn't pay for the extra bridge + publisher machinery — the MCP protocol already carries client identity at session start, and the daemon is a local socket where bridge-vs-protocol identification has no security delta.

3. **Mode signal: `LOCUTUS_MODE` env var on the bridge, forwarded to the daemon via `_meta["locutus.mode"]`.** Rejected bridge `--mode` CLI flag (more explicit but grows the bridge's CLI surface and requires updating every spawner; same end-state semantics). Rejected MCP-init-meta-only with no env or flag (defers the question of where the bridge learns the mode in the first place).

4. **Restriction lives at the tool's registration site (`requireRuntime` wrapper), not inside the handler body and not in tool descriptions only.** Rejected hardcoded checks in handler bodies — would scatter the runtime concern through unrelated code and obscure the rule. Rejected description-only enforcement (no structural backstop; a misreading of the description silently produces wrong behavior). The wrapper keeps the rule visible at one place per tool while leaving the handler runtime-agnostic.

5. **Unknown runtime treated as not-in-allowlist for restricted tools.** A connecting client whose `ClientInfo.name` isn't recognized cannot call restricted tools. Rejected "unknown → allow restricted" as the unsafe direction: restricted tools have a specific intended audience, and an unrecognized client is by definition not that audience. Unrestricted tools remain available to unknown runtimes — only the explicit `requireRuntime`-wrapped set is gated.

6. **Hacky-but-honest framing.** Returning a runtime-specific error from a tool that is otherwise runtime-agnostic is a compromise the SDK constraint forces. The wrapper at registration is the least-bad placement — it keeps the runtime concern out of handler bodies and concentrates it at one inspection point per tool. If the go-sdk later exposes per-session `tools/list` customization or per-session tool registration, the wrapper-at-registration pattern is the natural extension point: the same allowlist becomes the input to a `tools/list` filter without changing the handler.

**Alternatives considered:**

- **`tools.yaml` config + per-session `tools/list` filter + call-time guard.** The original draft. Rejected per RQ1 after discovering the SDK constraint: the file's primary consumer (the list filter) couldn't be built without forking the SDK, leaving the file as indirection over a single tool family's rule.

- **Custom JSON-RPC interceptor under the SDK that filters `tools/list` per-session.** Would restore the full original design including the list filter. Rejected as a significant new layer with its own correctness surface, not justified for one tool family. Re-evaluate if multiple runtime-scoped tool families emerge or if operators ask for per-project tool-exposure overrides.

- **Hardcoded runtime checks at the top of each restricted handler body.** Considered as the simplest possible mechanism. Rejected per RQ4 — scatters runtime concern through handler logic; the wrapper at registration is exactly as simple and centralizes the rule.

- **Description-only enforcement (no call-time guard).** Rejected per RQ4 — no structural backstop. A description is a hint, not a contract.

- **Bridge-passed `--runtime` flag + matching publisher emit.** Considered (option B in RQ2) for symmetric "(runtime, mode) flows the same channel as the publisher's per-runtime dispatch." Rejected per RQ2 — the parallel was driven by symmetry-for-symmetry's-sake rather than what works.

- **Per-runtime tool naming** (e.g., `claude_spec_loop_begin` vs `codex_spec_loop_begin`). Rejected — breaks the single-daemon design and forces the playbook prose to know which name to use per-runtime; the wrapper approach keeps tool names stable and runtime-agnostic.

- **Code (modify):**

  - `internal/mcp/tools_loop.go` — wrap each of the three `spec_loop_*` registrations in `requireRuntime("codex", "gemini")`, sharpen each `desc*` constant with the leading runtime-audience sentence.

- **Code (test):**
  - Session-context unit tests: `InitializedHandler` extracts runtime + mode from `clientInfo.name` + `_meta["locutus.mode"]`; missing mode → `"interactive"` default; missing client name → empty runtime → `requireRuntime` denies.
  - `requireRuntime` unit tests: allowed runtime → delegates to inner handler; denied runtime → returns MCP error naming runtime/mode/tool/docs-ref; unknown runtime → deny.
  - Integration test (in-memory MCP transports, two simulated sessions): a `claude-code` interactive session calling `spec_loop_begin` errors with the documented message; a `codex` interactive session calling the same tool succeeds and the shared loop store reflects the advance; the two sessions co-exist on the same daemon without state collision.

- **Follow-ups (separate DJs, tracked here):**
  - **DJ-144 placeholder — Provider vs runtime naming audit.** The codebase mixes provider names (`anthropic` / `googleai` / `openai`) — semantically correct in `models.yaml` and agent frontmatter `models:` arrays where the axis is model-selection — with runtime names (`claude-code` / `codex` / `gemini`) — semantically correct in publisher dispatch, MCP client identification, and tool restriction where the axis is the runtime binary. The two axes happen to align 1:1 today but aren't the same thing. A separate grep-and-doc DJ audits for mis-axis usage and pins the distinction in `docs/agent-conventions.md`.
  - **DJ-145 placeholder — Cross-runtime interactive delegation.** Today `agents-default.yaml`'s per-activity runtime mapping only governs the headless ACP-dispatch path; interactive sessions run in the host runtime regardless. A separate architectural DJ weighs whether interactive sessions should support cross-runtime delegation (e.g., a Claude Code session spawning a Codex ACP run for a specific activity), or whether the current "host runtime for interactive" semantics are the deliberate end-state. DJ-143's restriction scales cleanly to either resolution — a spawned cross-runtime session presents as its own runtime identity at MCP-connect.
  - **DJ-146 placeholder — Per-session `tools/list` filtering if the go-sdk gains support.** If a future go-sdk release exposes per-session `tools/list` customization or per-session tool registration, the `requireRuntime` allowlist is the natural input to also hide restricted tools from non-allowlisted sessions' lists. Today's design is forward-compatible — the wrapper at registration carries the allowlist that a list-filter would consume.
