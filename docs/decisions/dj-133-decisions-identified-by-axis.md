## DJ-133: Decisions Identified by Axis, Not Chosen Option (Eliminates ID/Content Drift After Flips; Collapses Replace-By-Axis-ID Logic; Bounds the Council's ID Namespace for Hallucination Defense)

**Status:** shipped 2026-05-23 — the axis-shaped decision ID convention (`dec-<axis-id>`) is foundational and carries forward through [DJ-134](dj-134-unified-spec-store.md) and [DJ-135](dj-135-multi-runtime-pivot.md). Every decision in the spec graph uses `dec-<axis>` form (verified empirically on winplan refine `~/projects/winplan/.locutus/sessions/20260526/1918/080000/`); the migration shipped as `internal/migrate/MigrateDecisionIDs` and is idempotent on subsequent `locutus update --offline --reset` runs. The MCP `spec_propose_decision` tool registered in DJ-135 backfills `axes` from the id when the agent omits it (per DJ-135 phase-5 convergence-by-construction discipline). CLAUDE.md's "Sources of Truth" section explicitly names this convention as authoritative.

**Context.** The seventh winplan re-run (`/Users/chetan/projects/winplan/.locutus/sessions/20260522/1250/10-877ef1/`) — the first run exercising DJ-132 plus the May 2026 model/SDK refresh — surfaced two distinct tool-loop failures where the decision-elaborator (in revise mode) and a feature-elaborator each spiraled through 10 spec_get / spec_search rounds chasing decision IDs that didn't exist in the graph. Round-by-round reasoning for the failed revise dispatch shows the model spec_searching `supabase`, summarizing the result as *"some other Supabase-related nodes: `dec-supabase-storage-tus-railway-ingestion`, `dec-supabase-postgres-persistence`, `dec-supabase-read-replicas-isolation`, `dec-axiom-pgaudit-logging`, and `dec-transaction-scoped-rls-context`"* — **every one of those five IDs is fabricated**. The model then spent seven more rounds spec_getting and spec_searching for them, each round returning not-found, never giving up, until the maxToolRounds cap fired.

Three immediate fixes landed in [eb51a14] addressed the proximal failure mode: extending the manifest with `origin` (settled/proposed) and `working` flags so the model can read state without guessing, inlining the kind-matched id list into spec_get not-found errors so recovery is bounded, and fixing stale agent-prompt text that told the model spec_get couldn't see in-flight decisions. But those fixes are mitigations on top of a deeper architectural issue the trace exposed: **the decision ID's job is to be a stable handle for the architectural question the decision answers; the current chosen-option-name-in-the-ID convention makes the ID describe the answer instead, so the ID drifts whenever the answer changes**.

Concrete manifestations of the drift:

- **Stale chosen-option in id after a Flip.** When `dec-nextauth-identity-and-rbac` flips its chosen option from NextAuth.js to Clerk, [internal/agent/workflow_spec_generation_dj124.go:1163](../internal/agent/workflow_spec_generation_dj124.go#L1163)'s replace-by-axis-ID path preserves the prior id verbatim — so the revised decision's `id` stays `dec-nextauth-identity-and-rbac` even though "nextauth" is no longer what it chose. Backreferences (`feat-X.decisions: ["dec-nextauth-identity-and-rbac"]`) keep pointing to the right decision body but advertise the wrong technology in the slug.
- **A whole subsystem exists just to compensate.** [axisIntersectionMatches](../internal/agent/workflow_spec_generation_dj124.go#L1294) walks the cartesian product of incoming-axes × existing-decision-axes to find which prior decision a revision targets — because the ID itself doesn't tell you. The `ambiguous` integrity violation that fires when axis sets overlap multiple decisions, the `axisIDsExceedingRevisionCap` cap-as-commit lookup, and the `DecidedAxesByIter` / `AxisRevisionCount` maps that track per-axis state all key off the axis, not the id. The id is effectively an alias.
- **The id namespace is unbounded for the model.** Because IDs encode chosen options, the model can plausibly imagine variants — `dec-supabase-postgres-persistence` is no less semantically valid as a slug than `dec-supabase-postgresql`. Under Gemini 3.5 Flash's tool-loop pathology (the failure mode the May 2026 fixes mitigate but don't eliminate), the model confabulates IDs of this shape from the surrounding context and chases them. Bounding the namespace by the scout's known-axis set — the canonical, finite set of "questions this iteration is deciding" — makes confabulation structurally infeasible.

**Decision.** Decision IDs become identical to their primary axis ID, prefixed `dec-` for backward compatibility with existing prefix-based routing. Each axis the scout surfaces produces exactly one decision whose ID is `dec-<axis-id>`; the chosen option lives in `title`, `chosen_option`, and the decision body's content fields — not in the ID.

Concrete shape (examples from a typical refine):

| Axis (scout's OpenAxis.ID) | Decision ID (post-DJ-133) | Title (chosen option) | Pre-DJ-133 ID (deprecated) |
| --- | --- | --- | --- |
| `database-and-spatial-storage` | `dec-database-and-spatial-storage` | "Supabase PostgreSQL with PostGIS" | `dec-supabase-postgresql` |
| `compute-platform` | `dec-compute-platform` | "Render PaaS" | `dec-render-compute-platform` |
| `identity-and-rbac` | `dec-identity-and-rbac` | "Auth.js with self-hosted sessions" | `dec-nextauth-identity-and-rbac` |
| `voter-file-ingestion-strategy` | `dec-voter-file-ingestion-strategy` | "Staging-to-Relational ETL with JSONB" | `dec-voter-file-staging-etl` |

The ID is **the question**; the body answers it. A Flip changes the body and the title; the ID and every backreference stay verbatim.

For composite-axis decisions (rare — a decision that genuinely commits to multiple axes at once, e.g. choosing AWS ECS Fargate as both `compute-platform` and `aws-region`), the convention is **primary-axis-as-ID**: pick whichever axis the elaborator's `rationale` treats as primary, use that for the slug, and list the secondary axes in the existing `axes[]` field. The composite framing is already documented in the elaborator prompt; the ID convention just picks one of the listed axes rather than synthesizing a new joined slug. Avoids parsing ambiguity from join syntax (`dec-compute-platform--aws-region`); accepts that the ID surfaces only the primary lens.

**Resolved design questions** (settled in chat 2026-05-22; coupled with the three-fix scoping decision):

1. **Defer DJ-133 behind the three immediate fixes.** The three fixes (manifest origin/working, spec_get inline recovery, prompt corrections) ship as their own focused change and stand on their own — they mitigate the hallucination failure mode regardless of the ID convention. DJ-133 is a deeper refactor that needs its own DJ + plan + migration; bundling them would have produced a sprawling change with mixed cost profiles. Sequencing them lets empirical validation (another winplan re-run) confirm the fixes worked before committing to the bigger ID-convention change.

2. **Decisions don't carry chosen-option in the ID.** The decision body's `title`, `chosen_option`, and `rationale` are the human-readable answer surfaces. The ID is the durable handle that doesn't change when the body changes. This is the load-bearing inversion versus today.

3. **Composite axes use primary-axis-as-ID, not joined slugs.** Composite is rare; the secondary axes are already recorded in `axes[]`. A joined slug like `dec-compute-platform--aws-region` invites parsing ambiguity (two hyphens? one?) and surfaces both lenses in the slug for no consumer benefit. Primary-axis-as-ID picks one, documents the rest in `axes[]`, and stays scannable.

4. **Existing on-disk decisions migrate as part of the landing.** Per [[feedback-no-back-compat-until-self-hosting]] the user runs `locutus update --offline --reset` before every operation, so a one-shot migration that walks `.borg/spec/decisions/`, renames each `dec-<chosen-option>` to `dec-<primary-axis>`, and rewrites all incoming refs in features/strategies/bugs/approaches is acceptable. The cascade-rewrite machinery from [DJ-088](dj-088-architect-emits-inline-decisions.md) does the ref rewriting; the rename is mechanical (walk `axes[0]`, build new id, rename file, update sidecars).

5. **The elaborator stops minting IDs.** Today's `spec_decision_elaborator` prompt says *"A stable slug derived from the chosen option, prefixed `dec-`, lowercase, hyphen-separated, three to five words"* and the example payload shows `dec-postgres-oltp-store`. Post-DJ-133 the prompt says *"Copy the axis ID verbatim, prefixed `dec-`"* — no slug-from-chosen logic. The example payload uses `dec-database-and-spatial-storage`. Simpler prompt, simpler example, no derivation work for the model.

6. **`replace-by-axis-ID` becomes `replace-by-ID`.** `axisIntersectionMatches` and the ambiguity-as-integrity-violation path retire. The revise dispatch's incoming `id` IS the axis; mergeDecisions's match becomes a hash lookup. Several state fields (`DecidedAxesByIter`, `AxisRevisionCount`, `LockedDecisionIDs`) can either keep their semantics under the same key namespace (since axis-id == decision-id now) or merge into one map; preference is to keep them as separate maps for forensic clarity, with the understanding that the keys overlap.

7. **The `working` flag from the three-fix change keeps its meaning.** Under DJ-133 the ID is stable across Flips by construction, so `working: true` cleanly means "the body is being rewritten right now" without the ID-stability caveat the three-fix change had to add. The user's original framing — "working == true should imply that the decision itself may change, even at the ID level" — narrows to "the body may change" since the ID is now invariant.

**Alternatives considered.**

- **Keep chosen-option-IDs; address the failure mode purely through the three fixes.** The mitigations (inline recovery, manifest tagging, prompt corrections) work well enough to bound the model's recovery surface. Cheaper (no on-disk migration, no workflow refactor) than DJ-133. Rejected because the underlying architectural awkwardness remains: `axisIntersectionMatches` complexity stays, backreferences continue to advertise stale chosen options, and the model's id-confabulation surface stays open. The three fixes are necessary regardless; DJ-133 closes the deeper issue once.

- **Joined-axis IDs for composite decisions** (e.g. `dec-compute-platform--aws-region`). Adds parsing ambiguity (one-hyphen separator collides with axis-slug-internal hyphens) for negligible benefit — operators can already see the full axis set in the `axes[]` field. Rejected for the principle that the ID should be the simplest stable handle, not a multi-key summary.

- **Synthesized hash IDs** (`dec-a7f9c3` etc.). Maximally stable; no information leakage. Rejected because operator UX matters: an ID that says nothing about what the decision is about makes `locutus history`, traces, and refs unscannable without follow-up `spec_get` calls. Axis-as-ID strikes the right tradeoff: stable AND scannable (the slug names the question).

- **Decision IDs become opaque UUIDs persisted at first-author time; axis IDs stay separate.** A variant of synthesized hash IDs where the lookup table maps axis → decision-UUID. Adds an indirection layer that doesn't pay for itself — the council already enforces 1:1 axis-to-decision (with composite 2:1 as the rare exception), so the indirection is solving a non-problem. Rejected.

**Consequences.**

Idempotent (already-axis-shaped IDs are no-ops). Logged to `.borg/history/` as a migration event.
    - Tests: existing `mergeDecisions` tests update for the simpler match path; `axisIntersectionMatches` tests retire; new tests for the migration path. The three-fix tests stay valid (their assertions are about manifest shape, not ID convention).

- **User-visible:**
    - **IDs in `locutus status` / `locutus history` / `locutus explain` are axis-named.** `dec-compute-platform` instead of `dec-render-compute-platform`. The decision's `title` continues to surface the chosen option in human-readable form ("Render PaaS").
    - **Backreferences are durable.** `feat-X.decisions: ["dec-compute-platform"]` continues to point to the right decision body across every Flip the council ever runs on that axis. Operators reading a feature's citations see "this feature depends on the compute-platform decision" — durably accurate regardless of which compute platform the current iteration chose.

    - `mergeDecisions` is mildly faster: hash lookup vs cartesian-product axis-intersection. The trace effect is sub-millisecond per axis at typical winplan-sized graphs (5-10 decisions); not user-perceivable.
    - Token cost per refine doesn't change. The elaborator's prompt is slightly shorter (no "pick the natural slug" guidance) but the JSON output is the same shape.

- **Migration:** one-shot on-disk migration runs automatically on the first `locutus update` after DJ-133 lands. Rewrites every persisted `.borg/spec/decisions/dec-<chosen>.json` → `dec-<axis>.json` and updates all incoming refs via cascade-rewrite. Existing-graph references inside agent prompts and DJ text are stale chosen-option-IDs; those are documentation and update as touched. Per [[feedback-no-back-compat-until-self-hosting]] no shim is necessary — the operator runs `locutus update --offline --reset` and proceeds.

- **Documentation:**
    - `CLAUDE.md` gains a sentence in the Sources of Truth section noting the axis-as-ID convention.
    - `docs/council.md` updates the `spec_decision_elaborator` per-agent reference to describe the new ID derivation rule (axis verbatim, prefix `dec-`) and removes any examples that used chosen-option IDs.
    - `docs/agent-conventions.md` may add a brief section on the stable-handle-vs-current-answer separation as a general convention — IDs name the question, content fields name the answer.

**Reversal criteria.** Revert if:

- (a) the migration produces incorrect refs at scale. A bug in the cascade-rewrite leaves features or strategies pointing at the wrong decision (e.g. two decisions had overlapping axes and the migration picked the wrong one for primary-axis-as-ID); operators discover stale refs after the next refine. Mitigation: the migration logs every rename + ref rewrite to `.borg/history/`; a `locutus history --kind=migration_decision_rename` view lets operators audit. If the rewrite logic has a structural bug, hard revert (restore from history).

- (b) the composite-axis convention proves operationally awkward. The primary-axis-as-ID picks one of N axes; the elaborator's `axes[]` lists all N, but consumers reading citations only see the primary lens. If operators consistently report confusion (e.g. an OPS engineer reading `feat-X.decisions: ["dec-compute-platform"]` doesn't realize the same decision also commits the `aws-region` axis), the convention may need to change — either back to a joined slug, or a richer "this decision spans axes X and Y" surfacing in the manifest. Mitigation: surface composite-axis info in the manifest entry's metadata (extend SpecManifestEntry with `axes []string` for decisions) before reverting the ID convention.

- (c) the bounded id-namespace doesn't reduce model hallucination. The deeper claim DJ-133 rests on is that bounding the id namespace by the scout's known-axis set defeats Gemini-3.5-Flash-style confabulation. If a post-DJ-133 winplan re-run still shows the model fabricating axis-named IDs that don't exist (`dec-some-other-axis-the-scout-didnt-surface`), the hallucination has different root cause than namespace-unboundedness. Mitigation: examine whether the new failure mode is "model invented an axis name" (in which case the scout's open-axis-set isn't bounding model attention) vs "model genuinely tool-looped on real IDs returning empty bodies" (a different bug). The latter is fixable; the former invalidates DJ-133's hypothesis.

- (d) elaborator prompt simplification regresses initial alternative quality. The post-DJ-133 elaborator prompt drops the "derive a natural slug from the chosen option" instruction. If empirical evidence shows the elaborator was using that derivation step as a forcing function for thinking about the chosen option's properties (a side effect of the slug exercise), removing it may degrade initial decision quality. Mitigation: keep an explicit "now state the chosen option clearly in `title` and `chosen_option`" step in the elaborator's task body so the surface attention to the chosen option stays — just route it to the right field instead of the ID slug.
