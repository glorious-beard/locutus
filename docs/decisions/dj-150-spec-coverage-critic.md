## DJ-150: `spec-coverage-critic` Surfaces Deliverable-Shape Obligations as Refine-Time Findings — Not as a New Graph Node Kind; Grounded Per-Deliverable Enumeration Mirrors DJ-132's Candidate-Survey Pattern; Features Are the Coverage Target Because Features Are the Recognized PM Artifact and Obligations Are Not; Architect's Revise Pass Extends Existing Feature Scope (Prose Coverage, No `covers` Citation Slice) or Proposes a New Feature to Close the Gap; Coverage Judgment Is Natural-Language Per-Run, Not a Structural Citation Check; Idempotent Across `refine goals` Re-Runs Modulo Grounded-Enumeration Stochasticity and Deliverable-Shape Stability; Triggered by WinPlan's Empty Home-Page Surface After the First End-to-End Adopt Run — `next build` Succeeded, 810 Vitest Tests Passed, `app/page.tsx` Was a 9-Line Placeholder Because No Feature Owned the Public Entry Surface; Codifies the "Topology vs Process" Bias-Check — New Node Kinds Earn Their Place Only When Each Corresponds to an Independently Recognized PM/Engineering Artifact (ADRs, Features, Design Docs, Goal Trees), Otherwise the Fix Lives in Prompts / Critics / Playbook Prose

**Status:** settled (designed 2026-05-31; no code yet). Follow-up to [DJ-149](dj-149-adopt-spec-to-code-reconciliation.md)'s first end-to-end adopt run against winplan, which surfaced a category-class gap that no DJ-149 mechanism could have caught: the rendered application had no usable surface at `/` because no feature in the spec graph owned the unauthenticated public entry experience. Synthesis was faithful to the spec; the spec didn't capture what makes a "hosted code with users" deliverable a *usable* web app.

**Context.** A spec graph's value as a quality scaffold for AI-driven code generation (per the [Locutus goal framing](../../../.claude/projects/-Users-chetan-projects-locutus/memory/project_locutus_goal_framing.md)) depends on the graph capturing what AI-generated code needs to be coherent over time — architectural choices, feature briefs, scope guards. The graph faithfully represents what was *decided*. It does not represent what was *assumed by virtue of the deliverable type*: that a web app for users has a public entry surface, that an API has a documented schema surface, that a mobile app has an in-app navigation system. These are category obligations — implications of the deliverable shape — that a human PM brings as tacit knowledge but the synthesizer cannot reliably surface from prose alone.

Winplan's first end-to-end adopt run made this concrete. After `refine` and adopt produced 23 stacked branches with 810 Vitest tests passing and `next build` clean, the rendered home page at `/` was nine lines: the product title, a one-sentence tagline, no navigation, no CTA. Every feature in the spec graph mounted under `[workspaceId]/...` or under an onboarding flow. None owned `app/page.tsx`. The system delivered exactly what the spec described; the spec described an authenticated product surface and implicitly assumed someone would write the unauthenticated entry.

The first reach (mine) was for a registry — `obligations-default.yaml` keyed by deliverable shape, listing the obligations each shape implies. The user pushed back: that pre-bakes my current understanding of "what a web app needs" and degrades to "the registry is incomplete for this project, skip the check." The second reach was for a new `obligation` graph node kind, persisted at `.borg/spec/obligations/`, cited via a `covers` slice on features. The user pushed back harder: obligations are not a recognized PM/engineering artifact. Decisions are ADRs, features are feature briefs, approaches are design docs, goals are goal trees — each has a real-world counterpart. Obligations would exist solely because the AI's gap-spotting is unreliable. Adding a node kind to fix an AI failure is accumulated complexity that future contributors cannot justify.

The right framing is therefore the third one: **the gap is in judgment, not topology**. The system needs a critic that enumerates category obligations at refine-time, judges coverage against existing features, and surfaces uncovered obligations as findings. The findings live in the critic's transcript; the architect's revise pass addresses them by extending existing feature scope (the feature's body grows to discuss the public entry surface) or proposing a new feature (which then enters the graph as the recognized PM-shaped artifact it is). No new persistent node kind, no `covers` citation slice on existing nodes, no registry. The structural fix to "the spec doesn't catch this" is *better gap-spotting at refine-time*, not *more graph topology to remember the gap*.

This approach has direct precedent. DJ-132 added `spec-candidate-survey` as a fast-tier grounded agent that enumerates axis candidates via web search; the decision-elaborator consumes the survey and resolves the axis. DJ-129 introduced dimension-driven critics that run alongside elaboration and surface dimension-specific findings (cost ceiling, observability posture, etc.). The coverage critic is the same shape applied to a different dimension: enumeration is per-deliverable-shape obligations rather than per-axis candidates; judgment is coverage-via-feature-body rather than choice-via-decision; output is findings rather than candidates. The pattern reuses existing infrastructure (grounded enumeration, dimension critics, refine playbook integration) without adding any new graph kind, MCP tool, or persistence path.

**Decision.** Add a `spec-coverage-critic` agent that runs once per refine iteration, after the architect has identified deliverable shapes and proposed features. The critic enumerates obligations for each identified shape via grounded web search (no canned examples, no enumerated lists in the prompt), then judges coverage by reading existing feature bodies in natural language. Uncovered obligations become findings; the architect's revise pass addresses each finding by extending an existing feature's scope or proposing a new feature. No new node kinds, no new MCP write tools, no `covers` slice on existing nodes, no registry.

1. **New agent: `spec-coverage-critic`.** Fast tier (Haiku 4.5 / Flash-Lite / gpt-5-mini), `grounding: true`, `thinking: off`. Front-matter `role: critic`. The agent receives the deliverable shape(s) identified by the architect (e.g., `hosted-code-with-users`, `mobile-app`, `firmware`) plus the current set of features and strategies. Its prompt body is positively phrased per [agent-conventions](../agent-conventions.md): the agent enumerates obligations the deliverable carries by virtue of its category — including obvious or minor ones — and grounds each obligation with at least one citation to an authoritative source (industry guidance, framework documentation, accessibility standards, etc.). For each enumerated obligation, the agent reads feature bodies and judges whether any feature's scope covers it. Output is a `CoverageReport` — an array of `{obligation_title, obligation_description, citations[], covered_by: [feat-id, ...] | [], rationale}` entries. The agent does not propose features itself; that is the architect's job on the revise pass.

2. **Coverage is judged by feature-body reading, not by a citation slice.** Features do not gain a `covers: [oblig-slug]` slice. The critic reads feature titles, summaries, and bodies in natural language and decides whether the obligation's concern is addressed within scope. This avoids creating persistent references to ephemeral obligation slugs (which would have to be stable across stochastic enumeration runs) and keeps the graph free of structural debt that exists only to support the critic's bookkeeping. The cost is that the critic re-judges coverage every run; the benefit is that the graph stays PM-shaped.

3. **Findings are session-state, not graph state.** The critic's `CoverageReport` is captured in the refine session's transcript (under `.locutus/sessions/<sid>/`) and surfaced to the architect's revise pass. Findings do not persist to `.borg/spec/`. A subsequent refine run will produce a fresh `CoverageReport` from a fresh critic dispatch; idempotency comes from feature-body stability (the architect's prior revise-pass extensions are still in the bodies) and grounded-enumeration stability (the critic's web-search-backed obligation list is similar run-to-run), not from persisted findings.

4. **Refine playbook integration.** Both `spec_refinement.md` and `code_assimilation.md` gain a new step after the architect pass and before the elaborator fan-out: dispatch `spec-coverage-critic` per identified deliverable shape (one critic dispatch per shape on multi-deliverable projects), collect the `CoverageReport`s, and feed any uncovered obligations into the architect's revise-pass input alongside the elaborator findings. The architect addresses each uncovered obligation by extending an existing feature's body to discuss the concern (when an existing feature is the natural fit) or proposing a new feature (when no existing feature reasonably covers it). The newly proposed feature lands via `spec_propose_feature` like any other feature — same shape, same MCP tool, same persistence.

5. **Drift cascade is unchanged.** When the architect's revise pass mutates a feature body, the existing DJ-138 cascade walker marks dependent approaches drifted via `SpecHashes` set-diff or hash-diff; the next adopt run picks up the drift and either regenerates the approach (DJ-149's `regenerate` worklist category, drives `approach-regenerator`) or implements a newly proposed feature's `synthesize_approach` entry (DJ-087 path). No new cascade machinery is needed; obligations participate via the features that close them.

6. **Stochasticity is bounded by grounding, not by persistence.** Per DJ-132's analysis, fast-tier grounded enumeration is reliable when each entry must resolve to a real source — the critic's output is constrained by the web-search citation discipline. Run-to-run variance in enumeration is acceptable: when an authoritative source adds a new category requirement (e.g., AI-disclosure surfaces becoming a category obligation for consumer web apps), the critic surfaces it as a new finding, and the operator decides whether to act on it. The system surfacing newly-emerged category requirements is correct behavior, not non-determinism to be suppressed.

7. **Multi-deliverable projects get per-deliverable critic dispatches.** Per [spec-architect.md](../../internal/scaffold/agents/spec-architect.md)'s axes-per-deliverable framing, a project can carry multiple deliverable shapes (a wearable: hardware + firmware + mobile companion + cloud backend + documentation). The critic dispatches once per identified shape; each enumeration is scoped to its shape's category obligations. Feature coverage judgment respects deliverable boundaries — a hosted-backend feature doesn't cover a mobile-app obligation by default; the critic's prompt makes that explicit.

8. **Test for "does this earn a new node kind?"** Codifies the topology-vs-process bias check the user surfaced in the design conversation: before proposing a new node kind in any future DJ, name the corresponding human-practice artifact (architecture decision record, feature brief, technical design document, goal tree, etc.). If no such artifact exists in standard PM/engineering practice, the proposal is hacking around an AI failure — find the prompt, critic, or playbook fix instead. New node kinds are reserved for structures that would exist in the graph even without AI involvement.

## Resolved design questions

1. **Registry of obligations per deliverable shape vs grounded enumeration per run.** Resolved in favor of enumeration. Registries bake in the author's current understanding and degrade silently when project shapes evolve; grounded enumeration discovers what THIS deliverable needs from authoritative sources and surfaces newly-emerged obligations as they appear. Locked-down convention belongs in registries for *system behavior* (`agents-default.yaml`, `runtimes-default.yaml`); it does not belong for *project category knowledge* that the system needs to discover.

2. **Obligation as new node kind vs feature as coverage target.** Resolved in favor of features. New node kinds must correspond to recognized PM/engineering artifacts. Obligations are not an artifact in any product-management methodology; they exist only because AI gap-spotting is unreliable. The fix is the critic that does gap-spotting better, not a node kind that records gaps. Features are the right size of artifact because they live at both ends of the human↔AI workflow: PMs and designers refine them (titles, mockups, Figma links, acceptance criteria); AI synthesizes approaches from them. Putting coverage on features preserves the artifact's role as the bridge.

3. **Prose coverage vs `covers: [oblig-slug]` citation slice on features.** Resolved in favor of prose. A citation slice would create persistent references to ephemeral obligation slugs that change between runs (slug stability becomes load-bearing); prose coverage lets the critic re-judge coverage from feature bodies each run. The cost is re-judgment work per run; the benefit is that the graph carries no structural debt that exists only to support critic bookkeeping. The critic's natural-language judgment is honest about what's happening: the critic is judging, the feature exists, the obligation framework is ephemeral.

4. **Critic dispatch timing in the refine pipeline.** After the architect pass (deliverable shape and initial feature set are known), before the elaborator fan-out (so uncovered-obligation findings flow into the elaborator's revise-pass input alongside other findings). Single critic dispatch per identified deliverable shape per iteration; multi-deliverable projects get multiple critic dispatches per iteration.

5. **What persists, what doesn't.** Features persist (existing PM-shaped artifact). The architect's coverage-driven feature revisions persist as feature-body changes (already handled by `spec_revise_feature`). Critic transcripts persist in `.locutus/sessions/<sid>/` (existing session log location). The obligation enumeration itself does NOT persist — it is re-derived each refine run from grounded enumeration. The `CoverageReport` is a transient artifact in the session log, queryable post-run via the session trace but not part of the spec graph.

6. **Idempotency claim across `refine goals` re-runs.** Effectively idempotent under three conditions: deliverable shape unchanged, grounded-enumeration produces a similar obligation set (modulo low-variance stochasticity), and feature bodies still cover the obligations they covered last run. When all three hold, the critic finds no uncovered obligations and the architect's revise pass has no obligation-driven work to do — a no-op for the obligations branch (the goal-layer-sync step in `refine goals` does its usual work regardless). When any condition fails (GOALS.md changes shape, authoritative sources add a new category obligation, a refine pass removed scope from a feature that previously covered an obligation), the critic correctly surfaces real work to do.

7. **Granularity discipline in the critic's prompt.** Obligations are *category requirements*, not *implementation tasks*. "Public entry surface" is an obligation; "landing page with hero section, CTA button, and value-prop above the fold" is an implementation. The prompt frames the critic's enumeration at the category level — if the model surfaces implementation-level entries, those collapse upward into a single category obligation. Avoids turning coverage check into a feature-level checklist that drowns the architect in findings.

8. **Critic output shape and validation.** `CoverageReport` is validated against a JSON Schema per the DJ-132 pattern; minItems on `obligations` is zero (a sufficiently spare deliverable may have no obligations to check, though this should be rare); each obligation entry requires non-empty `title`, `description`, `citations[]` (minItems ≥ 1 per grounded-enumeration discipline), and `covered_by` (which may be empty). The schema disallows free-form prose outside the structured fields per the agent-conventions structured-output discipline.

## Alternatives considered

- **Obligations as a registry (`obligations-default.yaml` keyed by deliverable shape).** Rejected. Pre-bakes the registry author's current understanding; degrades when project shapes evolve beyond the registry's coverage; requires manual maintenance as category requirements shift; conflates "system behavior" (which is what existing default registries describe) with "project category knowledge" (which the system needs to discover per project). Same anti-pattern as canned examples in prompts — DJ-132's web-grounded survey exists specifically to avoid this shape.

- **Obligations as a new graph node kind (`oblig-*` files in `.borg/spec/obligations/`).** Rejected. Obligations are not a recognized PM/engineering artifact in any methodology — the term appears nowhere in standard practice; the node kind would exist solely because AI gap-spotting is unreliable. Adding graph topology to compensate for AI failure modes accumulates complexity that future contributors cannot justify ("what is this for?" "because Claude was bad at noticing the absence of a home page in 2026"). Decisions are ADRs, features are feature briefs, approaches are design docs, goals are goal trees — each carries weight independent of AI involvement. Obligations would not.

- **`covers: [oblig-slug]` citation slice on features with no obligation persistence.** Rejected. Creates persistent references to ephemeral things — the slug `oblig-public-entry-surface` would appear on disk in feature frontmatter even though no `oblig-public-entry-surface` node exists; slug stability across stochastic enumeration runs becomes load-bearing for false-positive prevention; a critic that produces `oblig-public-entry-experience` instead of `oblig-public-entry-surface` one run later would mark previously-covered features as uncovered. The structural debt exists solely to support critic bookkeeping. Prose coverage avoids the entire problem.

- **Do nothing; rely on operator vigilance to spot category gaps.** Rejected as the long-term answer though it remains the short-term workaround (the operator can run `refine` themselves and add `feat-landing` manually). The quality-scaffold framing's whole point is that the system surfaces category gaps the operator might miss; relying on operator catch is the failure mode the scaffold is supposed to prevent. The critic is a fixable gap; leaving it open is accepting a known degradation in the scaffold's promise.

- **Fold coverage checking into the architect's prompt directly.** Considered. Argument: avoid a new agent dispatch by enriching the architect's prompt to enumerate obligations and check coverage itself. Rejected because the architect is already responsible for axis enumeration, feature proposal, strategy commitment, and inline-decision authoring; adding obligation enumeration + coverage judgment overloads the role and makes the prompt harder to maintain. DJ-129's dimension-critic pattern explicitly separates enumeration/judgment from authorship; the coverage critic follows that established split. The cost is one additional agent dispatch per refine iteration per deliverable shape (~$0.05-0.15 at fast tier with grounding); acceptable.

- **Persist `CoverageReport`s to `.borg/spec/coverage/<deliverable>-<run>.yaml`.** Considered. Argument: enable trend analysis (which obligations have been uncovered across the project's history?), enable cross-iteration consistency checks. Rejected for v1: persistence introduces graph topology to support analysis that may never be performed; the session-trace log already captures `CoverageReport`s as part of refine's session-state; if trend analysis becomes valuable, persistence can be added later without breaking the v1 design. YAGNI applies.

- **Run the coverage critic post-elaborator instead of pre-elaborator.** Considered. Argument: the elaborator may have already proposed coverage-aligned features that the architect's first pass didn't, so checking earlier surfaces non-issues. Rejected: the critic's findings need to flow into the elaborator's revise-pass input so the elaborator can address them in the same iteration. Post-elaborator dispatch would defer the architect's response to the next iteration, doubling the convergence cost for projects where the critic surfaces real gaps. Pre-elaborator dispatch keeps the work in one iteration.

## Consequences

### New files

- `internal/scaffold/agents/spec-coverage-critic.md` — the agent prompt. Fast tier, `grounding: true`, `thinking: off`, `role: critic`. Output schema validates `CoverageReport`. Positively phrased prompt body per agent-conventions; no canned obligation examples; explicit framing that the agent must enumerate obligations the deliverable carries *by virtue of its category* including obvious / minor entries; coverage judgment is per-feature-body reading in natural language.

- `internal/scaffold/agents/spec-coverage-critic_test.go` (or whatever the existing test pattern is) — verifies hyphenated-id invariant per DJ-135, verifies the front-matter shape, verifies the output schema validates the documented `CoverageReport` shape.

### Modified files

- `internal/scaffold/plans/spec_refinement.md` — add the critic-dispatch step after the architect pass, before the elaborator fan-out. The step receives the architect's deliverable-shape identifications and current features; dispatches the critic per shape; collects `CoverageReport`s; passes uncovered obligations into the elaborator's revise-pass input.

- `internal/scaffold/plans/spec_refinement.claude-code.md` — mirror the step in the dynamic-workflow overlay, expressed in workflow primitives (`parallel()` across deliverable shapes when multi-deliverable, single dispatch when single-deliverable).

- `internal/scaffold/plans/code_assimilation.md` — same step in the assimilate playbook, since assimilate also runs the architect (inferring features from code is symmetric to refining features from goals, per DJ-148's bidirectional-reconciliation principle).

- `internal/scaffold/plans/code_assimilation.claude-code.md` — same mirror.

- `internal/activity/agents-default.yaml` — register the critic agent for the refine and assimilate activities.

- `docs/council.md` — document the critic in the spec-generation council reference; update the workflow diagram to include the dispatch step.

- `docs/agent-conventions.md` — add a brief paragraph documenting the topology-vs-process bias check (DJ-150 §8) as a project-wide convention applicable to future DJs.

- `CLAUDE.md` — add a new bullet under "Sources of Truth" naming DJ-150's contribution and the topology-vs-process discipline.

- `docs/DECISION_JOURNAL.md` — manifest row added.

### Not changed

- `internal/spec/` — no new node kind, no new struct, no new fields. Approach, Feature, Strategy, Decision, Goal, AntiGoal, Bug unchanged.
- `internal/mcp/tools_spec_*.go` — no new write tools, no new read tools, no new input shapes. Existing `spec_propose_feature` / `spec_revise_feature` handle feature creation and scope extension; that is the whole graph mutation surface the coverage critic drives.
- `internal/agent/spec_store.go` — no new entry kind, no new persistence path. Critic findings live in session state, not store state.
- `internal/state/` — unchanged. State records remain the etcd-equivalent for reconciliation; coverage is a refine-time property, orthogonal to reconciliation.

### Operational

- Refine cost increases by one fast-tier grounded agent dispatch per deliverable shape per iteration. Estimated at $0.05-0.15 per dispatch; multi-deliverable projects pay multiples of that. At fast tier with grounding the call is fast (~3-8 seconds); not a noticeable iteration-time impact.
- Refine iteration count may grow when the critic surfaces real gaps (the architect's revise pass has additional work, which may not converge in the previously-typical iteration count). This is the correct behavior — surfacing real gaps takes real work to close.
- The first refine pass on existing projects (winplan included) will surface obligations that were previously implicit; the operator may see new features proposed (or existing features revised) that they didn't anticipate. Documentation should set this expectation at DJ-150's rollout.

### Quality

- Resolves the winplan empty-home-page surface (the trigger). On a re-refine, the critic would enumerate `public-entry-surface` (or equivalent), find no covering feature, and surface the gap; the architect would propose `feat-landing` (or whichever shape fits); adopt would synthesize an approach and implement.
- Generalizes to brownfield projects via assimilate — when `assimilate` infers features from existing code, the coverage critic checks them for category-obligation coverage and surfaces gaps the existing code may not have addressed (or that the inference may have missed).
- Codifies the topology-vs-process discipline as a project-wide quality property (§8) — future DJs are now expected to apply the test before proposing new node kinds.

## Future Work

- **DJ-15X: Cross-iteration consistency monitoring of grounded enumeration.** If practice reveals high run-to-run variance in the critic's enumeration (e.g., 20%+ of obligations differ between consecutive runs on a stable project), add a consistency check that compares the current `CoverageReport` against the prior iteration's and flags significant churn for operator review. v1 does not include this; bet is that fast-tier grounded enumeration is stable enough that the simple model holds. Promote to a real DJ if measurements show otherwise.

- **DJ-15X: Granularity-normalization pass on critic output.** If practice reveals the critic emitting too-fine-grained obligations (implementation-task level rather than category level), add a normalization step that collapses fine entries into category-level parents. v1 relies on prompt-level granularity discipline; a structural normalization step is the escape hatch if prose discipline proves insufficient.

- **DJ-15X: Coverage critic for state-level obligations.** The current scope is spec-level category obligations (what the deliverable shape implies). A future critic could check state-level obligations — e.g., is there a `live` approach covering the public entry surface, not just a `feat-landing` node? This blurs the spec-vs-state separation DJ-068 established, so v1 stays spec-only. Worth revisiting if operators report that "feature exists but no state record" is a common silent failure.

- **DJ-15X: Surface obligation-coverage rationale on feature bodies.** The critic's coverage judgment is captured in session state; making the rationale visible on the feature itself (as a generated comment in the body, opt-in via a flag) would aid future reviewers who wonder why a feature's scope includes a particular concern. Considered, deferred: adds prose that the agent must maintain through revisions, with unclear upside. Promote if reviewers report difficulty tracing feature scope to category obligations.

- **DJ-15X: Apply the topology-vs-process test retroactively.** This DJ codifies the bias check for future DJs. A retrospective audit of existing DJs to identify any that introduced a node kind that fails the test would be valuable as a one-time cleanup. The most likely candidates to audit: ones where the rationale focused on AI failure modes rather than human-practice artifacts. Not in scope here; surfaced as a separate maintenance pass.
