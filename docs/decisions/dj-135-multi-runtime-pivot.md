## DJ-135: Locutus Pivots from In-Process Council to Activity-Driven Multi-Runtime Execution via ACP and MCP (Council Becomes a Coding-Agent-Executed Playbook; Locutus Retains the Spec Graph + Activity Registry; agents.yaml Drives Per-Activity Runtime Selection with Detection-Based Fallback; Per-Project Singleton MCP Server Coordinates Shared State; Tools Are the Universal Read/Write Floor + Resources the Additive Human-Attach Surface; Supersedes the WorkflowExecutor-Based Council Architecture; Subsumes [DJ-127](dj-127-spec-mutation-tools-mcp.md)'s Write-Tools Design as the Foundation Layer)

**Status:** shipped 2026-05-26 — Phases 1-7 landed across 2026-05-25 / 2026-05-26 (per the implementation plan at `.claude/plans/dj-135-multi-runtime-pivot.md`). Empirical validation across two successful winplan refine runs: the first run on 2026-05-25 produced the 27 / 9 / 6 baseline; the second run on 2026-05-26 at `~/projects/winplan/.locutus/sessions/20260526/1918/080000/` identified the engineering-process / operations / business axes missed by round 1, converged in 3 iterations, and grew the graph to 42 / 12 / 10 — demonstrating that sequential refines productively compound on prior results. The Go-driven council architecture this DJ retired had never produced a clean convergent run on a representative project (`~/projects/winplan/.locutus/sessions/20260523/1920/18-f5bf96/` was the latest of many SUCCESS-without-output runs); the pivot meets the core hypothesis. Declared baseline 2026-05-26 — all prior DJs whose machinery this DJ subsumed or superseded are status-flipped in the same sweep. Follow-on refinements tracked under follow-up DJs (currently DJ-136 per-runtime idiomatic dispatch, in design).

**Context.** Twelve DJs in five weeks ([DJ-124](dj-124-decisions-before-narrative.md), [DJ-125](dj-125-in-flight-manifest.md), [DJ-126](dj-126-decision-revision.md), [DJ-128](dj-128-deliberation-log-and-cap-as-commit.md), [DJ-129](dj-129-dimension-driven-critics.md), [DJ-130](dj-130-provider-mechanics-and-trace-layer.md), [DJ-131](dj-131-phase-fanout-collapse.md), [DJ-132](dj-132-candidate-survey-agent.md), [DJ-133](dj-133-decisions-identified-by-axis.md), [DJ-134](dj-134-unified-spec-store.md), DJ-103 fill-summaries refinements) have been increasingly tactical responses to a structurally fragile execution model: each addressed a real failure but the cumulative effect is +30 knobs, +10 failure surfaces, and convergence still doesn't reliably land on the first try. Each individual DJ defended its addition; the *trajectory* didn't. Chat 2026-05-23 surfaced the underlying pattern as patch-treadmill — the same DX pathology Locutus was originally designed (in the GaitLab era) to break the operator out of, now reproduced inside Locutus's own development loop.
\
The substantive work the council performs (technical-PM-grade research, grounded option enumeration, axis surfacing, cross-decision integrity checking, per-iteration re-examination) is *correct* and is the load-bearing differentiator versus one-way spec-driven-design tools — confirmed in chat 2026-05-23-24. What's brittle is the *execution layer*: a Go-encoded WorkflowExecutor that orchestrates multi-agent debate inside a single Locutus process, with per-call format-pass splits, retry loops, integrity-revise architects, cap-as-commit gates, and provider-specific tuning baked into prompts. The winplan trace at `~/projects/winplan/.locutus/sessions/20260523/1920/18-f5bf96/` is the proximate evidence: the council surfaced 6 axes correctly, the architect's reasoning pass produced an integrity-clean repair for all of them, but the format pass on `gemini-3.1-flash-lite` silently dropped the entire decisions array — and the run reported SUCCESS without writing anything to disk, because the integrity loop chased a ghost the format pass created upstream.
\
External validation: the Stack Overflow Developer Survey 2025 ([survey.stackoverflow.co/2025/ai](https://survey.stackoverflow.co/2025/ai/)) data shows multi-tool AI usage is structural (ChatGPT 81.7% + Copilot 67.9% + Gemini 47.4% + Claude Code 40.8% sum to ~238% among agent users — average user runs 2-3 tools). Anecdotal HN/Reddit data: subscription-rate-limit hopping is a known pattern; task-specific tool preferences are real (Claude Code for autonomous work, Cursor for IDE-tight edits, Codex for OpenAI-ecosystem integration, Gemini for grounded research). But: most developers drive one agent at a time within a session, switching only when blocked. The dominant usage is *sequential single-runtime sessions with state on disk as the handoff medium* — which is exactly the shape that fits a spec-graph mutation server backed by Locutus's SpecStore. And the user's own daily experience with Claude Code, despite its frustrations, is more productive than the brittle Locutus council — partly because Claude Code solves a smaller problem (one agent, one human in loop) and partly because Anthropic owns the prompts + tools + model alignment end-to-end.
\
The transport layer for delegating to coding agents already shipped: [DJ-119](dj-119-agent-client-protocol-replaces.md) replaced the per-CLI NDJSON drivers with an Agent Client Protocol (ACP) client (`github.com/coder/acp-go-sdk`). The capability matrix across the three primary ACP servers (Claude Agent for Claude Code, Codex's `codex-acp`, Gemini's native `gemini --acp`) is verified. The published ACP registry ([agentclientprotocol.com/get-started/registry](https://agentclientprotocol.com/get-started/registry)) covers 40+ coding-agent runtimes including Cursor, Copilot, Cline, Auggie, Goose, etc. — ACP-first portability isn't aspirational, it's the working substrate. Each runtime exposes subagent + skill + slash-command + MCP primitives natively; the file shapes differ slightly (Claude Code uses markdown + YAML frontmatter; Codex uses TOML; Gemini uses markdown), but the per-agent prompt content is portable across all three with a translation pass at publish time.
\
The pivot the data supports: **Locutus stops trying to be the council orchestrator inside a single Go process. It becomes (a) the spec graph + activity registry on disk, (b) an MCP server exposing the spec mutation surface, (c) a publisher that emits per-runtime subagent files + activity playbooks at scaffold time. The execution of an activity becomes the responsibility of a coding agent — either spawned by Locutus via ACP (CLI path) or already running and calling into Locutus (slash command / MCP path). The council shape, the agent prompts, the convergence discipline — all retained. What retires is the WorkflowExecutor + Go-encoded orchestration + per-iteration format-pass split + integrity-revise architect.**

**Decision.** Reframe Locutus as three layered components, each with a clear deployment shape:

1. **Spec graph + activity registry on disk** — `.borg/spec/`, `.borg/agents/`, `.borg/plans/`, `.borg/history/`. Version-controlled. The durable, queryable, team-shared layer. This is what survives across sessions, runtimes, and operators.

2. **Per-project singleton MCP server** — `locutus mcp --project .` boots a long-lived process bound to `.locutus/mcp.sock`. Every MCP client (VS Code, Claude Code, Codex CLI, slash commands, subagents) connects to the same singleton. One SpecStore in memory, shared across all connections; in-flight transaction state visible across parent agent and subagents. Exposes:
    - **Tools (universal floor)** — full read + write surface for the spec graph. Reads: `spec_list_manifest`, `spec_get(ids)`, `spec_search(query)`. Writes: `spec_propose_decision`, `spec_propose_feature`, `spec_propose_strategy`, `spec_revise_*`. Activity triggers: `locutus_refine_goals`, `locutus_plan_feature`, etc. Tools work on every MCP host regardless of capability negotiation.
    - **Prompts (orchestration playbooks)** — `refine_goals`, `plan_feature`, etc. Returns the activity playbook as a multi-turn message sequence the calling LLM executes. Lets the *calling agent* dispatch subagents per the playbook; Locutus never spawns a duplicate worker when there's already an agent in the loop.
    - **Resources (additive ergonomic surface, where hosts support them)** — `spec://manifest` for the human-attach case + live-update stream. Per-node resources skipped (too granular for attachment; agents use `spec_get` instead). `notifications/resources/updated` fires on commit so dashboards re-render.
    - **Notifications** — `notifications/progress` is the primary visible streaming surface (renders inline in VS Code chat); `notifications/message` carries structured event data for downstream consumers (logged in VS Code output channel; consumed by future dashboards / aggregators).

3. **Activity executors** — the layer that runs an activity playbook against a coding agent. Three trigger paths converge on the same playbook artifact (`.borg/plans/<activity>.md`):
    - **CLI** (`locutus refine goals`): Locutus picks a runtime from `agents.yaml`'s prioritized list (filtered by what's detected on the system), spawns it via ACP, hands it the published subagents + playbook. The spawned agent executes the playbook; calls back into Locutus's MCP tools to mutate the graph.
    - **Slash command** (`/refine-goals` in Claude Code, Codex, etc.): the calling agent loads its published `.claude/commands/refine-goals.md` (or `.codex/commands/refine-goals.toml`, or `<gemini-ext>/commands/refine-goals.toml`) which points at the canonical playbook. The local agent executes; calls into Locutus's MCP tools.
    - **MCP prompt** (`prompts/get locutus.refine_goals`): Locutus returns the playbook as a prompt response. The calling LLM reads it and executes inline, dispatching its own subagents and calling Locutus's MCP tools.

Across the three trigger paths the rule is uniform: **Locutus never tries to be the council itself; the calling agent always dispatches.** The CLI path adds one extra step at the front (bootstrap a calling agent via ACP because there isn't one).

**Resolved design questions** (settled across chat 2026-05-23 and 2026-05-24):

1. **The council shape is right; the execution layer is what's brittle.** The substantive work agents do (researching, grounding, surfacing axes, challenging choices, re-examining design against goals) is what Locutus's value-prop rests on and what differentiates it from one-way spec-driven-design tools. Don't change the council shape; change what executes it.

2. **Convergence-by-construction returns as the design discipline** — the GaitLab-era motivation. The playbook framing says "assume best-practice defaults on open axes; do not surface to human unless explicitly challenged" as one-line plan discipline. Coding agents driving the playbook can ground assumptions via web search + cite them; human intervention is for *challenging* a decision after the fact via refine, not gating each decision before it lands.

3. **Activity-driven configuration, not verb-driven.** `agents.yaml` maps activities (spec_refinement, planning, frontend_implementation, backend_implementation) to prioritized runtime preferences. Detection-based fallback selects the first available runtime from the list. Per-activity granularity matches the empirical task-tool fit data; the runtime selection lives in config, not in Locutus's Go code.

4. **Per-project singleton MCP server with Unix socket coordination.** N subagents in one project share one Locutus process; the parent agent's in-flight transaction state is visible to subagents that read the graph mid-execution. Stdio-per-client breaks this; the singleton + socket bootstrap (`.locutus/mcp.sock` discovery; daemon fork on absence; idle-out after N minutes of no connections) makes the playbook architecture work. Operators see the standard `.mcp.json` config across all clients — Locutus handles lifecycle internally.

5. **Three trigger paths converge on one playbook artifact.** CLI trigger spawns runtime via ACP because no calling agent is present; slash command and MCP prompt are both "calling agent already in loop" cases where Locutus returns/exposes the playbook for the local agent to dispatch. No path duplicates orchestration work; the canonical `.borg/plans/<activity>.md` is the source of truth across all three.

6. **Publishing emits per-runtime copies, not symlinks.** File formats actually differ (Codex TOML vs Claude/Gemini markdown); frontmatter fields differ; runtime-specific tooling/model translation happens at publish time. Symlinks can't bridge these gaps. Canonical at `.borg/agents/<name>.md` in Locutus's format; publisher emits `.claude/agents/locutus/<name>.md`, `.codex/agents/locutus-<name>.toml`, `<gemini-ext>/agents/locutus-<name>.md`. Same lifecycle as existing `.borg/` scaffolding: `locutus init` creates initially; `locutus update --reset` regenerates.

7. **Subdirectory namespacing where the runtime supports it (Claude Code recursive scan of `.claude/agents/`); filename prefix elsewhere.** Verified: Claude Code's [subagent docs](https://code.claude.com/docs/en/sub-agents) state subdirectories are scanned recursively and identity comes only from frontmatter `name`. Codex and Gemini's docs don't document nesting; safer to assume flat and prefix.

8. **Hyphenated naming throughout (`spec-scout`, not `spec_scout`).** Claude Code *requires* lowercase + hyphens (no underscores allowed). Gemini accepts both; Codex's examples use underscores but no documented constraint. Hyphens are the only choice that works on all three; existing Locutus canonicals (`spec_scout`, `spec_decision_elaborator`, etc.) get renamed mechanically. Internal Go references update to match; the agent ID, the published filename, the frontmatter `name` — all consistent hyphenated form, no per-runtime translation needed beyond format conversion.

9. **Tools are the universal floor; resources are an additive ergonomic surface where hosts support them.** MCP host capability matrix varies (Claude Code: ✓ both; VS Code Copilot: ✓ tools, partial resources; Codex/Cursor/Gemini variable). Tools work everywhere; resources are best-effort better-UX. Asymmetric exposure (reads only via resources) loses functionality on hosts without resource support; symmetric exposure (reads via both) gives graceful degradation. The duplication tax is small — same SpecStore projection in two adapters.

10. **`notifications/progress` is the primary visible streaming surface for VS Code (and others); `notifications/message` is the structured-event surface for downstream consumers.** Verified against VS Code source: `notifications/progress` consumed by `McpTool._callWithProgress` and rendered inline in chat panel during a tool call. `notifications/message` written to that MCP server's output channel via the logger service — not inline but accessible for forensics. Pack visible status in `progress.message`; pack structured event payloads (agent ID, decision summary, axis, span ID) in `message.data`.

11. **Lifecycle matches existing `.borg/` scaffolding** — `locutus init` creates from embedded defaults (or on MCP server startup if `.borg/` and `.locutus/` are missing); `locutus update --reset` regenerates from embedded defaults (or `/locutus-update reset` as a slash command). No new conceptual surface — provider-specific dirs are additional publish targets in the same pipeline.

12. **`.locutus/` for ephemeral runtime state; `.borg/` for version-controlled artifacts.** Per existing convention. The `mcp.sock`, `mcp.pid`, session traces, and any other runtime-scoped files land under `.locutus/` and inherit its gitignore status. `.borg/` stays the durable, team-shared layer.

13. **Flat-subscription economics retire several tactical fixes from prior DJs.** The shift from per-call token-cost concerns to amortized subscription cost (via runtime-driven LLM calls inside coding agents rather than Locutus's own direct-SDK adapter) removes pressure for: cap-as-commit ([DJ-128](dj-128-deliberation-log-and-cap-as-commit.md)); the thinking/format split ([DJ-130](dj-130-provider-mechanics-and-trace-layer.md)); revision-count revision caps; the projection token-minimization rationale; the candidate-survey-as-cheaper-than-richer-elaborator framing ([DJ-132](dj-132-candidate-survey-agent.md)). Most of these mechanisms either retire (when no longer load-bearing) or stay as discipline (when they encode a real cognitive separation independent of cost).

14. **Per-runtime overrides for prompts are deferred.** The agent-conventions discipline aims for portable prompts; the publisher handles format translation. Per-runtime prompt tweaks (`.borg/agents/spec-scout.codex.md` overrides) are a future escape hatch only; v1 ships with no override surface. DX hit accepted: "modify the per-runtime published file directly, knowing it's overwritten on `update --reset`" is tolerable until forward-deploy machinery earns its weight.

15. **A2UI output skipped for v1.** Researched and rejected for the no-human-in-loop philosophy: most of A2UI's value is interaction; structured display components are duplicative of what MCP notifications + session traces already provide as structured JSON. Revisit if a specific A2UI-capable client (web dashboard, IDE extension) materializes.

**Alternatives considered.**

- **Keep the Go-driven council; keep tuning parameters.** Each parameter knob (model tier per agent, retry caps, prompt phrasing, format-pass tier, revision caps) gets tuned individually as failure surfaces; iterate to convergence. Rejected after explicit identification of the patch-treadmill pattern in chat 2026-05-24 — twelve DJs in five weeks landed real fixes but did not converge on reliability because the failure modes are endogenous to multi-agent debate over non-deterministic LLM stacks with format-pass risk. Each individual fix is defensible; the trajectory isn't.

- **Pure singleton model, no CLI path.** Locutus only runs as an MCP server; all activity execution requires a coding agent client. Rejected: scripted / headless / non-interactive use cases (CI, batch processing, ad-hoc operator commands) still need a CLI surface, even if the CLI's implementation spawns a coding agent via ACP internally.

- **A2UI for output.** Considered for richer console + dashboard rendering. Rejected: most of A2UI's value is interaction (forms, approvals), incompatible with the no-human-in-loop philosophy. Display-only A2UI is duplicative of MCP notifications + persisted trace artifacts. Re-evaluate when a specific A2UI-capable client emerges.

- **Symlinks for agent definitions across runtime locations.** Considered for single-source-of-truth simplicity. Rejected: file formats actually differ (Codex TOML vs Claude/Gemini markdown); frontmatter fields differ per runtime; symlinks can't bridge format conversion. Per-runtime publisher emits real copies.

- **Per-runtime prompt overrides at canonical-definition time** (`.borg/agents/spec-scout.codex.md` shadows `.borg/agents/spec-scout.md` for Codex specifically). Considered for fine-tuning prompts per provider's idiosyncrasies. Deferred: drift risk + complexity outweigh benefit at v1; agent-conventions discipline aims for portable prompts. The future forward-deploy machinery is the right escape hatch when it earns its weight.

- **Resources-only for spec graph reads** (no read tools). Considered for clean separation between "reads = passive context" and "tools = active actions." Rejected: MCP host capability matrix varies; hosts without resource support lose read access entirely. Tools are the universal floor.

- **Tools-only with no resources at all.** Considered for surface-area minimization. Rejected: loses the human-attach UX (operator wants to grok the manifest in their VS Code chat without writing tool calls) and the future live-update stream for dashboards via `notifications/resources/updated`. Additive resources are worth the small duplication tax.

- **Per-client stdio MCP subprocesses (N+1 processes for N subagents + parent).** Considered for MCP-spec idiom simplicity. Rejected: SpecStore in-flight state is per-process; subagents' reads can't see the parent agent's in-flight transaction; multi-process atomic-write coordination only works at commit boundaries which doesn't match the playbook's read-after-write pattern. Singleton + Unix socket is the only model that supports the playbook architecture.

- **Defer the pivot; ship more incremental DJs.** Considered for risk mitigation. Rejected after the user named the patch-treadmill pattern explicitly. Each incremental DJ has been *individually* defensible; the cumulative trajectory has not improved convergence reliability. Continuing the same pattern produces more DJs and the same convergence fragility. The pivot is the structural answer.

- **Performance:**
    - **Wall-clock per refine increases** in absolute terms (coding agents have their own latency profiles; ACP round-trips add overhead). Empirically the bottleneck shifts from "how fast can Locutus iterate" to "how fast does the coding agent dispatch its subagents."
    - **Token cost moves off Locutus's books.** Coding agents call their own LLMs under their own subscription; Locutus doesn't pay per-call. This is the load-bearing economic shift.
    - **Convergence reliability is the metric.** Empirical hypothesis: coding-agent-driven execution converges more reliably on the first try than the Go-encoded council, because (a) coding agents are engineered for the exact "follow plan, dispatch subagents, iterate to completion" workload, (b) no format-pass split risk for multi-section outputs, (c) the calling agent's human-in-loop (when present) catches issues earlier. Verifying this is the v1 validation criterion.

    - **Direct cut, no fallback retained.** The current Go council has never produced a clean convergent run on a representative project — the winplan trace at `~/projects/winplan/.locutus/sessions/20260523/1920/18-f5bf96/` is the latest of many SUCCESS-without-output runs. Keeping it as fallback would signal an expectation that it's useful and would split engineering attention between two paths. Per [[feedback-no-back-compat-until-self-hosting]], operators run `locutus update --offline --reset` and proceed on the new path. The Go council code (WorkflowExecutor, dispatcher, direct-SDK adapters, council bookkeeping) deletes in the same phase that lands the playbook path — no intermediate fallback mode.
    - Spec graph on disk is unchanged (DJ-134's SpecStore + `.borg/spec/` persistence carries forward). No data migration required.
    - Agent prompt rename pass is a one-shot mechanical change; the rename lands before the publisher runs, so the publisher writes hyphenated names from the start.

- **Documentation:**
    - `CLAUDE.md` gains a new top-level section on the pivot — the source-of-truth shift (Locutus is now MCP server + activity registry, not in-process council), the activity → runtime mapping via agents.yaml, the publisher's role, the MCP surface (tools/prompts/resources), the singleton lifecycle. The existing "DJ-134" section stays; DJ-135 layers on top.
    - `docs/council.md` rewrites substantially. The per-agent prompt content is preserved but the "council workflow" framing changes from "Locutus orchestrates the council" to "the council runs as a playbook executed by a coding agent." Mermaid diagrams update.
    - `docs/agent-conventions.md` gains a section on per-runtime publishing (what translates, what doesn't), naming convention (hyphens), and the playbook authoring guidance.
    - `docs/debugging-traces.md` updates: traces during an activity now live in the calling agent's surface (e.g., Claude Code session log) augmented by Locutus's own `.locutus/sessions/` (which capture MCP tool calls only). The trace shape changes meaningfully.
    - New `docs/activities.md` documenting the activity registry, agents.yaml schema, runtime detection, publisher behavior, lifecycle.

**Reversal criteria.** Revert if:

- (a) **Multi-runtime portability proves illusory.** If each runtime requires significant per-agent prompt tweaks that defeat the canonical-prompt + publisher-format-translation model, the per-runtime override surface we deferred becomes mandatory immediately; the publisher's complexity grows; and the value-prop of "author once, run anywhere" collapses. Mitigation before reversal: stand up per-runtime override files as the escape hatch; verify portability empirically on the 2-3 most-used runtimes. The 80/20 case is what matters; rare per-runtime quirks are tolerable.

- (b) **The singleton MCP server's Unix socket bootstrap proves unreliable in real deployments.** Edge cases: stale socket from a crashed daemon, permission errors on the socket file, cross-OS portability (Windows named-pipe equivalents), socket collisions on shared filesystems. Mitigation before reversal: comprehensive bootstrap test suite, fall back to stdio-per-client mode with the documented "in-flight state visible only at commit boundaries" caveat. The playbook architecture would lose its in-flight cross-subagent visibility but other functionality survives.

- (c) **The playbook model produces less reliable convergence than the Go-driven council.** If empirical comparison on winplan (or a representative second project) shows the coding-agent path produces lower-quality specs, more dangling refs, more incomplete iterations, or longer time-to-completion than the Go council — the structural pivot's core hypothesis fails. Mitigation before reversal: tune the playbook + subagent prompts (which are still under our control); compare specifically the convergence rate, the citation grounding, and the integrity of cross-references. If after meaningful playbook tuning the Go path still wins, the council shape may need to stay Go-orchestrated even though the rest of the pivot lands.

- (d) **ACP capability gaps in real-world runtimes block activity execution.** [DJ-119](dj-119-agent-client-protocol-replaces.md)'s Phase 0 verification confirmed Claude Agent, Codex, and Gemini support the long-lived-session + multi-prompt pattern this design relies on. If subsequent runtime upgrades (or other runtimes we add) drop capabilities we depend on (session/load, structured tool calls, MCP-server discovery from inside ACP sessions), specific activities or runtimes may degrade. Mitigation before reversal: per-runtime capability detection + degraded modes; explicit documentation of unsupported runtime/activity combinations in `agents.yaml`.

- (e) **The MCP capability matrix shifts such that resources or notifications become widely unavailable.** Today's reasoning assumes tools-are-universal-floor + resources-are-additive. If a major host drops tool support in favor of an entirely new primitive, or if MCP's future evolution renders our chosen surface non-portable, the surface choice would need revisiting. Mitigation: the spec graph + activity registry on disk is the durable layer; MCP is the wire. If MCP becomes non-viable, replace the MCP server with another wire shape without losing the underlying data.
