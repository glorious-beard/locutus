## DJ-134: Unified In-Process Spec Store Supersedes the Swappable-Wrapper Stack (Eliminates SwappableSpecSearch / SwappableSpecListManifest / SwappableSpecGet / FSSpecProvider / InFlightSpecStore; Single Mutex-Protected Store Backs Both On-Disk Persistence and In-Flight Council Mutations; Prepares the Read Surface for Tool-Call-Driven Spec Mutation)

**Status:** shipped 2026-05-23 — the unified SpecStore is the foundation layer that [DJ-135](dj-135-multi-runtime-pivot.md)'s entire MCP server tool surface runs against. No structural change required for DJ-135 — the SpecStore's per-entry typed origin tag (settled / proposed / working) is exactly what the MCP `spec_get` / `spec_search` / `spec_list_manifest` tools expose. Empirically validated against winplan refine on 2026-05-26 (`~/projects/winplan/.locutus/sessions/20260526/1918/080000/`) where the playbook-executed council mutated the store through MCP tool calls and the resulting graph rendered correctly. Phases 1-4 landed 2026-05-23 (commits `3f336dd`, `6accb0c`, `374b173`, `d0e1107`).

**Context.** The eighth winplan re-run sequence — five trace folders across `~/projects/winplan/.locutus/sessions/20260522` through `20260523` — exposed a latent bug that had been quietly burning tokens since DJ-125 Phase 3 shipped (2026-04 timeframe). The cmd-layer at [cmd/llm.go:188-228](../cmd/llm.go#L188-L228) wraps the production `*Executor` in `LoggingExecutor` (recording, DJ-130) and `NotifyingExecutor` (sink emission); `specgen.go`'s [specSearchSwap / specListManifestSwap / specGetSwap](../internal/agent/specgen.go#L370-L404) helpers type-assert the **outer** wrapper at council start to find the swappables to push the in-flight overlay into. Neither wrapper carried `SpecSearch() / SpecListManifest() / SpecGet()` pass-through methods, so the type assertions silently failed, the council's `Swap(inflightStore)` never landed, and every `spec_*` tool call in a council run fell through to the FS-backed default for the entire run. The in-flight overlay was invisible to the model. The fix in commit [`52e16fd`](https://github.com/chetan/locutus/commit/52e16fd) added the pass-through methods; convergence in the next trace ([20260523/1339/40-fd0046](file:///Users/chetan/projects/winplan/.locutus/sessions/20260523/1339/40-fd0046/)) dropped from 10-round reconciler spirals to 2 rounds with the reconciler reasoning *"The manifest confirms this, showing everything as 'proposed' and 'settled' in this iteration"* — empirical proof both that the bug was real and that the fix closes it.

But the fix is a patch on a deeper design problem. The user's design critique in chat 2026-05-23: *"you chose to take a far more complicated route simply for the sake of preserving existing design, rather than taking the approach of actually solving the problem. The problem was that the store needed to surface both settled and in-flight specs. This was a poor decision to make some weird wrapper on top of the existing store. It resulted in this bug that was missed for multiple DJs as we struggle to achieve convergence, wasting tokens during the whole time. You over-indexed on keeping existing code over actually solving the problem we faced."* That critique names the load-bearing failure: the swap-and-wrap pattern was the wrong primitive. Whenever a layered wrapper chain meets a swap-based hot-replace primitive, the type-assertion plumbing becomes a silent-failure surface — every new wrapper has to remember to expose every swappable, or the swap silently no-ops.

Concrete manifestations the current design carries:

- **Two parallel hierarchies for the same data.** [SpecManifestProvider / SpecGetProvider](../internal/agent/spec_inflight_swap.go#L33-L44) name the read surface in interface form; [fsSpecProvider](../internal/agent/spec_inflight_swap.go#L48) and [InFlightSpecStore](../internal/agent/spec_inflight_swap.go#L76) are the two concrete implementations; [SwappableSpecListManifest](../internal/agent/spec_inflight_swap.go#L529) and [SwappableSpecGet](../internal/agent/spec_inflight_swap.go#L568) are the swap shells the registry sees; [SwappableSpecSearch](../internal/agent/spec_search_swap.go#L28) is the third, structurally identical, swap shell for the search index. The wrapper-pass-through methods on [LoggingExecutor](../internal/agent/session.go) and [NotifyingExecutor](../internal/agent/notifying_executor.go) bring the count of types you have to keep in sync to **nine** for one logical capability (read spec nodes).
- **The in-flight overlay only reads the persisted graph by reference-snapshotting it at council start** ([InFlightSpecStore.SetState](../internal/agent/spec_inflight_swap.go#L127)). Edits the council performs to spec nodes via the future write-tool surface ([DJ-127](dj-127-spec-mutation-tools-mcp.md)) would have nowhere to land — the overlay holds `rawProposal` text + an `ExistingSpec` snapshot, not a mutable store. To support mutation-via-tool-call, the overlay would either need to grow its own write path (duplicating the FS path) or punch through to the underlying FS provider, both of which deepen the wrapper layering rather than collapsing it.
- **The swap-and-restore lifecycle is council-scoped** ([generateSpecWithWorkflow](../internal/agent/specgen.go) calls `Swap(inflight)` at council start and `Swap(prev)` in a defer at council end). Non-council read paths — `locutus explain`, `locutus justify`, future write-tool dispatches outside a council — go through the same swappable but always see the FS-backed default. The swap is solving "make council reads see council writes" by hot-replacing the entire read backend rather than by making the store understand which writes are durable vs in-flight.
- **The bug surface scales with wrapper count.** DJ-130 added LoggingExecutor; DJ-131 (when it ships) will add a phase-fanout executor wrapper; future observability or quota-enforcement wrappers will compose around those. Each new wrapper that doesn't expose every swappable accessor reintroduces the silent-no-op failure mode. The pass-through methods are unenforced convention — Go's type-assertion-via-anonymous-interface gives no compile-time check that a wrapper covers every swappable surface its inner executor exposes.
- **Tool-call-driven spec mutation is on the near-to-medium-term roadmap** (chat 2026-05-23). [DJ-127](dj-127-spec-mutation-tools-mcp.md) frames spec_create / spec_update / spec_delete tools as the surface coding agents and councils alike will use to mutate the graph. Layering write tools on top of the current read-stack would require: a fourth swappable (`SwappableSpecWrite`), a fourth pass-through method on every wrapper, a fourth provider interface, and answering "does the in-flight overlay accept writes or proxy to FS?" — every dimension the read stack already has, doubled.
- **The read API itself encodes a sequential-fetch pattern that has empirically exhausted the tool-loop cap.** The eighth winplan re-run trace at `~/projects/winplan/.locutus/sessions/20260523/1347/33-a750b3/calls/0049-spec_scout/` shows the scout's iter-3 pass exceeding the 10-round Gemini tool-use cap because the model was issuing single-id `spec_get(id)` calls one-per-round across 8 open concerns × ~1-2 referenced nodes each. The prompt explicitly directed *"use spec_get(id) to fetch any node body you need to inspect before disposing each concern"* and the model followed literally. A separate `spec_get_many` sibling tool would leave the single-id variant in place — and the model picks the simpler-shaped tool by default. The right forcing function is to remove the scalar-id variant entirely: spec_get accepts `ids: []string`, returns `{found, missing}`, with no scalar variant for the model to fall back to. DJ-134 makes this the contract on `SpecStore.GetSpec` from day one, not a follow-up refactor.

The single-store framing the user proposed in chat is the actual solution: *"I thought this would be something as simple as creating an in-memory store at the start of the operation seeded with the existing specs already committed to disk, and then as nodes are created for proposals, update the in-memory store. Protect store reads and writes with a simple mutex."*

**Decision.** Collapse the read-side spec surface to **one type**: `SpecStore`. The store is a single in-process, mutex-protected data structure that holds the full spec graph (decisions, features, strategies, bugs, approaches) plus per-node `Origin` (settled / proposed) and `Working` flags. Reads serve every consumer — RAG tools (spec_list_manifest, spec_get, spec_search), CLI verbs (`explain`, `justify`, `status`), MCP read tools. Writes serve every producer — the council's merge helpers when emitting in-flight proposals, the existing FS-backed persistence layer when materializing decisions to disk at council teardown, and (in the future) tool-call-driven mutation by agents.

Construction lifecycle:

- At process start, `SpecStore.New(fsys)` loads every node from `.borg/spec/` into memory. All loaded nodes start with `Origin: settled`. The store is registered with the tool registry once — there is no swap, no wrapper, no delegate replacement.
- The council seeds proposed nodes into the same store as it produces them (the merge helpers call `store.Put(node, OriginProposed)` instead of mutating a string-form RawProposal). Reads through the tool surface see settled + proposed in one manifest.
- At council teardown (or explicit promotion via the reconciler), proposed nodes flip to settled and the store flushes the delta to `.borg/spec/` via a single transactional `Persist()` call. The FS path becomes a write-back of the in-memory store rather than a parallel data source.
- Outside a council, mutating CLI verbs (`refine`, `import`, `adopt`'s synthesis writeback) interact with the same store. The store is the single source of truth in-process; the FS is its persistence backing.

The wrapper-pass-through bug becomes structurally impossible: there is no swappable to forward through wrappers. `LoggingExecutor.SpecSearch()` and its siblings retire alongside the swappables they pass through. The tool registry holds one `*SpecStore` reference; wrappers neither see it nor need to expose it.

The search index becomes a derived view on the same store. The store maintains the Bluge index as a write-through projection — every `store.Put` updates the in-memory index synchronously under the same mutex window. `SwappableSpecSearch` and `search.InFlightIndex` retire; there is one index, kept in sync with the store at every write, used by every reader.

**Resolved design questions** (settled in chat 2026-05-23 + design pass during DJ-134 draft):

1. **One store, not two-with-an-overlay.** The chat critique is the load-bearing framing. The existing settled-vs-in-flight distinction is preserved as a **per-node tag** on entries inside the single store, not as two stores with a wrapper deciding which to read. The manifest renderer reads `entry.Origin` from the node it already has in hand; no separate provider dispatch.

2. **The mutex is fine.** Worried-about-contention RWMutex with the read side held briefly during `ListManifest` / `GetSpec` / `Search` matches the existing `InFlightSpecStore.snapshot()` pattern's contention profile. Writes during a council come from the workflow goroutine (single producer) and reads come from concurrent tool dispatches (multiple consumers); RWMutex is the right primitive. Empirically the existing `sync.RWMutex` in `InFlightSpecStore` and `SwappableSpec*` shapes carries no observed contention — the unified store inherits that profile.

3. **Writes durably land at council teardown, not per-merge.** The store mutates in memory throughout the council run; only at successful convergence does a single `Persist()` call write the proposed-and-promoted nodes to disk. Failed councils (max-iterations, context cancellation) discard the in-memory delta and the FS stays at its pre-council state. This preserves DJ-088's all-or-nothing council-output semantics; the current `RawProposal` string-form discard-on-failure becomes a structured `store.Discard()` on the same semantic boundary.

4. **The Bluge index is a write-through projection, not a separate swap.** Every `store.Put` updates the index synchronously. The cost is one Bluge `Update()` per node mutation (microseconds, dominated by the JSON-marshal step the merge helpers already do); the benefit is the search-index-currency bug class disappears. `search.InFlightIndex` retires entirely; the production-side `search.Index` becomes the index the store maintains.

5. **Tool-call write surface (DJ-127) lands on the unified store.** When DJ-127's spec_create / spec_update / spec_delete tools ship, their handlers call `store.Put` / `store.Update` / `store.Delete` directly — same surface the council uses, same locking discipline, same persistence path. Tool-driven writes outside a council immediately go to `Persist()` (single-write durability); tool-driven writes inside a council go to the in-memory tag-as-proposed pool and follow the same convergence-or-discard lifecycle as merge-driven writes.

6. **The `Working` flag stays.** The DJ-125 / commit [`eb51a14`] `Working` flag (an entry being rewritten this iteration) becomes a field on `SpecStore.Entry` directly. Computed by the workflow's merge closures via `store.MarkWorking(id)` calls rather than a separate `workingSignals` struct surfaced through a side-channel — same semantics, fewer indirections. The compute-from-OpenAxisIDs-and-OpenConcernDecisionIDs logic carries over verbatim.

7. **Migration is internal.** No on-disk format change. No prompt change. No agent-config change. The `.borg/spec/` layout, RawProposal JSON shape, and tool-call API are all stable. This is purely an internal-types refactor — the entire surface area is `internal/agent/` plus a small `cmd/llm.go` wiring shift. Per [[feedback-no-back-compat-until-self-hosting]] there's no shim concern.

8. **Wrapper pass-through methods retire.** [LoggingExecutor.SpecSearch / SpecListManifest / SpecGet](../internal/agent/session.go) and the matching [NotifyingExecutor](../internal/agent/notifying_executor.go) methods delete with the swappables they pass through. Future wrappers (DJ-131 phase-fanout, future observability) have nothing to forward; the silent-no-op failure mode is structurally closed.

**Alternatives considered.**

- **Keep the swap stack; add compile-time enforcement of wrapper pass-through.** A linter / go-generate pass would emit pass-through stubs for every wrapper that wraps an `AgentExecutor` exposing the spec-tool accessors. Cheaper than DJ-134's collapse (no architectural change), addresses the bug. Rejected because: (a) it leaves the parallel-hierarchies and overlay-vs-FS layering intact, so the underlying-design problem persists; (b) the DJ-127 write-tool surface still has to thread through every wrapper as separate methods; (c) the design overhead of maintaining the generator + ensuring every new spec-related capability gets added to it doesn't scale. The bug surface shrinks but doesn't close; the architectural complexity continues to grow.

- **Per-call context-passed store.** Instead of registering the store with the tool registry, pass it through `context.Context` on every call. Tool handlers extract via `SpecStoreFromContext(ctx)`. Eliminates the registry-coupling but introduces a different problem: every tool call site (CLI verbs, MCP server, council dispatches) must remember to plumb the store. Rejected because forgetting-to-plumb is the same shape of silent failure as forgetting-to-expose, just at a different layer. Single registry registration is the right invariant.

- **Opaque DB-backed store (SQLite / BoltDB).** The unified store becomes a persistence boundary rather than an in-memory cache + write-back. Single source of truth on disk; readers and writers both go through the DB layer; no in-memory delta. Rejected for two reasons: (a) the council's all-or-nothing semantics (DJ-088) maps cleanly to in-memory + commit-on-success but awkwardly to DB transactions that span N agent dispatches with arbitrary failure points; (b) `.borg/spec/` as committable git-trackable JSON is a load-bearing operator-facing format. DB-backing would either duplicate that surface (DB + git-trackable export) or replace it (lose human-readable diffs). DJ-134 keeps `.borg/spec/` as the persistent surface; the in-memory store is a read-write cache with single-writer-per-process discipline.

- **Keep `InFlightSpecStore` but delete the swappables; have the tool handlers reach into the store directly via a process-wide singleton.** Singleton drops the registry indirection. Rejected — singletons make tests brittle (every test that constructs spec tools shares state with every other test). The store-as-registered-dependency model the rest of the tool registry uses is the right pattern; DJ-134 keeps it.

- **Defer DJ-134 behind DJ-133's empirical validation.** A scheduling alternative: ship DJ-133 (axes-as-decision-IDs) first, confirm the convergence improvements in another winplan run, then tackle DJ-134. Tempting because DJ-133 is already in flight and DJ-134 is a deeper refactor. Rejected because the wrapper-pass-through bug already shipped — token cost continues to accrue silently in any future wrapper that forgets to expose a swappable. Once DJ-127's write-tool surface lands, the cost of DJ-134-later balloons (more swappables to retire, more wrapper methods to delete). DJ-134 is best landed soon after DJ-133 ships, while the design context is fresh and before write tools deepen the layering.

- **User-visible:** none. The CLI surface, MCP tool surface, on-disk format, and prompt surface are unchanged. The only observable difference is `locutus refine` and `locutus import` complete a hair faster (one less indirection per tool dispatch — submilli at the worst-case rates).

- **Performance:**
    - **Reads** are slightly faster (one fewer pointer-chase per tool dispatch — the swappable's RLock + delegate-fetch retires).
    - **Writes** are slightly faster per merge step (no JSON marshal-and-store-and-reparse round-trip through the `RawProposal` string; the store holds typed nodes already).
    - **Memory** is approximately unchanged. The current design holds the parsed proposal in `InFlightSpecStore.existing` plus the RawProposal string plus the search index documents; DJ-134 holds the parsed nodes once plus the search index documents. Net: one fewer copy of the proposal text in memory during a council run.
    - **Concurrency contention** is approximately unchanged. The single RWMutex protects roughly the same code regions that the existing three RWMutexes (one per swappable) plus the store-internal RWMutex protect today. Read-side lock holds are dominated by the lookup work, not the lock acquisition.

- **Migration:** none required. The refactor is internal-types-only; on-disk format, agent prompts, schema shapes, CLI verbs, MCP tool shapes are all unchanged. A `locutus update --offline --reset` after DJ-134 lands swaps the binary; the first council run uses the new store; nothing else moves.

**Reversal criteria.** Revert if:

- (a) **The single-mutex contention profile measurably regresses council throughput.** DJ-134's design assumes the existing per-swappable RWMutex contention is dominated by lookup work, not lock acquisition. If post-DJ-134 traces show council runs slowed by >10% wall-clock or per-tool-dispatch latency increases meaningfully under the unified mutex, the lock granularity is wrong. Mitigation: sub-divide the store's mutex by kind (decisions / features / strategies separately) before reverting. The unified-types argument survives finer-grained locking.

- (b) **The write-through index projection becomes a hot path under concurrent merges.** Today's `rebuildInFlightIndex` re-indexes the whole proposal on every merge; DJ-134's write-through model updates the index incrementally per `store.Put`. If incremental updates accumulate Bluge state in a way the per-merge rebuild didn't (memory growth, segment proliferation), the projection becomes a regression rather than an improvement. Mitigation: batch the index updates per-merge (collect-then-flush) before reverting; the store-as-source-of-truth argument survives the projection-strategy change.

- (c) **Council-failure-discard semantics regress.** Today's failed council leaves no on-disk side effects because `RawProposal` is in-memory text the workflow discards. DJ-134 preserves the same semantic via `store.Discard` not calling Persist. If a future workflow change accidentally calls Persist on a failed council — write-through-to-disk inside merge helpers, premature Persist on partial convergence — the failure-discard property breaks and partial graph state lands on disk. Mitigation: enforce Persist-only-at-explicit-council-end-with-success-flag as a structural invariant (a `committed bool` arg, no default-true path); the property is preservable, the regression mode is a usage bug not a design bug.

- (d) **DJ-127 write tools surface design conflicts with the store API.** DJ-134's `Put / Update / Delete` are designed for council-merge-driven writes; DJ-127's tool-call-driven writes have stricter validation (the model can't, e.g., create a decision without a chosen axis). If the store API turns out to need a separate "validated mutation" surface for tool calls vs the "trusted mutation" surface the workflow uses, the unification was premature — two write surfaces still simpler than five swap-and-wrap types, but the symmetry argument loses some force. Mitigation: layer validation as a thin wrapper around `Put` (the tool handler validates before calling); the underlying store stays one type. Reversal only triggers if validation requirements force two structurally-different storage shapes.
